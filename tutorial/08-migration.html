教程 08 · 迁移指南：升级到 React Native 0.87.1 ​

目标：把一个存量 RN 项目分阶段、可回退地升到 0.87.1。每一步都能独立验证，任何一步失败都能回到上一个绿色检查点。 配套阅读：07 · 更新日志（"改了什么"）与 React Native Upgrade Helper（模板文件逐行 diff）。

一、迁移前评估 ​

1.1 先确认你的起点 ​

bash
npx react-native info          # 看当前 RN / Node / JDK / Xcode / SDK 版本
1
当前版本建议路线
0.85 / 0.86直接升 0.87（跨度最小，0.86 无用户侧破坏性变更）
0.84先升 0.86 验证一轮，再升 0.87；0.84 已 EOL，不建议停留
≤ 0.80先逐个中间版本爬到 0.86（每升一版跑通一次），不要跨大版本直冲
仍在旧架构（Paper/Bridge）0.87 中新架构是唯一架构——必须先在 0.84~0.86 完成新架构迁移

1.2 分支与回退策略 ​

bash
git checkout -b chore/rn-087-upgrade
# 约定：每个阶段结束都是一个可运行的 commit，便于 bisect 与回退

4.2 三方库版本矩阵（本教程组件篇已验证组合） ​

库兼容版本不兼容时的症状
react-native-reanimated4.7.03.19.5 在 0.87 下编译失败（hermes/inspector-modern 头路径重构）
react-native-worklets0.13.0（Reanimated 4 的新搭档）缺包直接红屏
react-native-gesture-handler3.3.0手势 API 类型对不上
react-native-screens4.28.0原生编译/链接错误
react-native-safe-area-context≥ 5.8.1（5.10.0 已验证）早于 5.8.1 的 jest mock 在 Strict API 下类型报错
@react-navigation/native7.4.1 + 各 navigator 7.x—

升级顺序建议：先升 reanimated/worklets/gesture-handler/screens 这类带原生代码的库（它们决定 pod install 与 NDK 构建能否过），再升纯 JS 库。

bash
# iOS：依赖变更大时干净重装 Pods
cd ios && rm -rf Pods Podfile.lock && pod install && cd ..

4.3 带原生代码的库的排查法 ​

  • 查库的 release notes 是否写明支持 RN 0.87 / new architecture；
  • 未提供 Package.swift 不影响 CocoaPods 路径（那是 SwiftPM 实验路径才需要）；
  • 任何库报 TurboModule not found：装完必须完整重新构建（热更新不带原生代码，见06 章急救手册）。

5.4 已移除 API 逐项替换 ​

tsx
// ① InteractionManager 移除 → requestIdleCallback
// ❌ InteractionManager.runAfterInteractions(() => doWork());
// ✅
requestIdleCallback(deadline => {
  doWork();                       // 浏览器/RN 同款空闲回调
}, { timeout: 500 });

// ② useColorScheme 不再返回 'unspecified'
const scheme = useColorScheme();
// ❌ if (scheme === 'unspecified')
// ✅ null 即"跟随系统/未指定"
if (scheme === null) { /* 用默认主题 */ }

// ③ Appearance 的 'unspecified' 已弃用 → 'auto'
Appearance.setColorScheme('auto');

// ④ ScrollView.keyboardShouldPersistTaps 只接受字符串
<ScrollView keyboardShouldPersistTaps="handled" />   // 不再写 true/false

// ⑤ StatusBar 被移除的 Android 属性：改用原生主题/Activity 配置
// ❌ <StatusBar backgroundColor="transparent" translucent />
// ✅ 在 android 主题里设置 windowTranslucentNavigation / edge-to-edge

// ⑥ NativeMethods 类型 → HostInstance / 具体 Instance 类型

// ⑦ ImageBackground 弃用（仍可用，提前改）：
// ✅ 等价写法
<View>
  <Image source={bg} style={StyleSheet.absoluteFill} />
  {/* 子内容 */}
</View>

5.5 逃生舱（只在被三方库卡住时临时用） ​

jsonc
// tsconfig.json —— 回退旧类型，仅有效到 0.88，务必建技术债工单跟踪
{
  "compilerOptions": {
    "customConditions": ["react-native", "react-native-legacy-deep-imports"]
  }
}
1
2
3
4
5
6
  • 它只影响你自己项目的 TS 分析，不影响运行时；
  • 保持 skipLibCheck: true（@react-native/typescript-config 默认开启），避免三方 .d.ts 的错误淹没你；
  • 单个不兼容库（典型：库自带 jest mock 源码）可用 tsconfig paths 指向一个 declare const x: unknown; export default x; 的存根临时绕过，并给库提 issue。

5.6 配置与测试入口清扫 ​

  • metro.config.yaml/.yml 或 .es6 配置 → 改名 metro.config.js（或升级为 metro.config.mts）；
  • jest preset 改为消费独立包 @react-native/jest-preset；
  • polyfill 入口 react-native/rn-get-polyfills → @react-native/js-polyfills；
  • 删除自研代码里对独立 react-devtools WebSocket 连接的说明/脚本，统一用 RN DevTools。

六、阶段 3：Android 原生配置 ​

6.1 AGP 9 适配 ​

对照 Upgrade Helper 更新 android/build.gradle.kts 的 AGP 插件版本（9.x）与 Gradle wrapper 版本。当前过渡期在 android/gradle.properties 加：

properties
android.builtInKotlin=false
android.newDsl=false
1
2

这两个开关在 AGP 10 时会消失——把"迁移到新 DSL / 内置 Kotlin"列入后续计划，别当成永久配置。

6.2 SDK / Kotlin 版本 ​

kotlin
// android/app/build.gradle.kts —— 以模板 diff 为准，关键数字：
android {
    compileSdk = 37          // 原 36 → 37
    // minSdk 24、targetSdk 36（RN 0.87 模板值）
}

  • 自研原生模块 / 公司内库：minCompileSdk 必须 ≥ 34，否则发布检查会拦截；
  • Kotlin 语法层面 2.0 兼容；若模块用了 KAPT，注意评估向 KSP 迁移的计划（KAPT 在新 Kotlin 中维护趋缓）。

FAQ ​

Q1：能不能跳过 0.86 直接从 0.84 升？ 技术上 Upgrade Helper 能给出直接 diff，但 0.84→0.87 叠加了 Strict API 与 AGP 9 两重断裂，排查成本极高。强烈建议在 0.86 停留一个验证周期。

Q2：Expo 项目怎么升？ 0.87 通过 expo canary 提供；Expo 项目按 SDK 逐个升（SDK 57 对应 RN 0.86），不要在裸工作流里手动拉 RN 版本。

Q3：迁移后包体变大/启动变慢？ 先确认 Release 构建而非 Debug；再做一次干净重装（Pods/Gradle/Metro 三缓存）。0.87 的 Metro 内存与 source map 改进、TurboModules 懒加载在方向上是减负的，回归多为缓存或双架构并存配置残留。
