教程 20 · 性能、兼容与上线复盘：把活动安全地放出去 ​

目标：用构建产物和可复现的开关逻辑，把"首屏、弱网、低端机、灰度、回滚、监控、复盘、合规"串成一条上线闭环。 版本锚点：Vite 7.1.12、React 19.2.3、TypeScript 5.9 严格模式；性能数字来自本机 Node 24 / Vite 构建，不是真机数据。 前置：17 · 工程骨架、18 · 抽奖与风控、19 · 分享与海报。

前 19 章把活动"做出来了"。这一章回答最后一个问题：怎么证明它可以放出去，以及放出去之后出事怎么办。

活动 H5 的上线窗口通常只有一两天，没有 App 那种"发版—审核—全量"的缓冲。所以它的质量保障必须前移到构建期能测的、开关能控的、看板能看见的。凡是只能靠"上线后观察"的，都要提前准备好回滚。

一、首屏预算：用构建产物说话 ​

1.1 先看真实产物体积 ​

原型执行 vite build 的原始输出（Vite 7.1.12）：

产物原始gzip是否首屏必需
vendor-react-*.js193.9 KB60.5 KB是
index-*.js12.4 KB5.0 KB是
feature-poster-*.js4.1 KB2.0 KB否（点击后加载）
index-*.css2.2 KB1.0 KB是

首屏 JS 合计约 65.5 KB（gzip）。这个数字说明两件事：

  1. React 本体占了 92%，业务代码优化到极致也挤不出多少；
  2. 真正的优化空间在"不加载什么"，而不是"把业务代码写短"。

1.3 关键资源：能内联的内联，能预加载的预加载 ​

活动页首屏只有三样东西是关键的：主 KV、首屏文案、抽奖按钮。

资源策略原因
主 KV按设备档位选 WebP / JPEG，尺寸 ≤ 档位预算通常是首屏最大的一块
字体只用系统字体，或子集化后 font-display: swap中文字体动辄 3–8MB
JS / CSS由 Vite 注入 modulepreload减少串行等待
海报底图 / 二维码不预加载，点击生成时再取不是首屏所需

原型的降级层已经提供了"按预算挑图"的纯函数，第 17 章讲过，这里只强调顺序：先降图片，再降动画，最后才降主流程。

1.4 首屏指标怎么定 ​

指标建议目标说明
FCP（首次内容绘制）< 1.5s（4G，中端机）先看到内容，哪怕只是骨架
LCP（最大内容绘制）< 2.5s主 KV 或标题
INP（交互到下一次绘制）< 200ms点"抽奖"到有反馈
CLS（累计布局偏移）< 0.1骨架屏尺寸对齐就是为了这个

这些是通用建议值，不是本原型的实测结果。原型的构建产物体积是实测的，真机 FCP/LCP/INP 没有测。

二、弱网与低端机：降级要写进代码，不是写在文档里 ​

2.1 三档策略 ​

ts
// 原型：activity-h5-demo/src/core/degrade.ts（节选）
export function buildPolicy(signals: DeviceSignals): DegradePolicy {
  const tier = detectTier(signals);
  switch (tier) {
    case 'low':
      return { tier, richAnimation: false, decorativeEffects: false, wheelAnimation: 'none', preloadImages: 0, imageBudgetKB: 120, reasons };
    case 'mid':
      return { tier, richAnimation: false, decorativeEffects: true, wheelAnimation: 'fade', preloadImages: 1, imageBudgetKB: 220, reasons };
    default:
      return { tier, richAnimation: true, decorativeEffects: true, wheelAnimation: 'spin', preloadImages: 3, imageBudgetKB: 400, reasons };
  }
}

改 width、top、box-shadow 都会触发重排或重绘，在中低端机上直接掉帧。转盘、弹窗、按钮反馈全部用 transform / opacity，是活动页最划算的一条性能纪律。

will-change: transform 要慎用：用多了会常驻合成层，低内存机型反而更容易崩。

2.3 长列表与滚动：活动页也可能有"列表" ​

抽奖记录、奖品列表、排行榜都可能变长。超过约 100 条就应该虚拟滚动，否则：

  • 首屏渲染 500 个 DOM，滚动直接卡死；
  • 图片全部请求，弱网下 LCP 无法达标。

虚拟滚动的实现不在本章范围，但选择标准要写清楚：列表项高度固定用定高虚拟列表，高度不固定就用"分组 + 分页"，不要硬上不定高虚拟列表。

四个高频问题：

问题现象处理
弹窗层级中奖弹窗被海报或固定按钮盖住统一定义 z-index 阶梯（内容 1 / 悬浮按钮 50 / 弹窗 100 / Toast 200）

键盘弹起iOS 上输入框聚焦后页面被顶飞、弹窗错位输入类页面用 visualViewport 监听，或把输入区放在页面顶部

原型只实现了层级与安全区，滚动穿透与键盘行为未在真机验证。这两项在 iOS 微信里表现差异很大，必须在真机上过一遍。

2.5 返回刷新与状态保持 ​

用户在微信里点开分享、看完、返回，活动页会被重新加载（或走 bfcache）。两种处理：

  • 重新加载：依赖服务端返回的 drawsLeft 与记录，前端不缓存关键状态。这是最稳的做法，原型采用它。
  • bfcache 恢复：监听 pageshow 的 event.persisted，恢复时重新拉一次配置，避免展示过期次数。

不要用 localStorage 缓存"剩余次数"来省一次请求——用户在多标签、多设备下会看到不一致的数字。

三、灰度与回滚：开关要能真的止血 ​

3.1 三层开关 ​

原型的配置里只有两个字段，但它们对应三层控制：

层字段关掉之后
活动总开关drawEnabled抽奖入口置灰，页面与规则仍可读
流量灰度grayPercent未命中用户看到"活动未开始"
奖品级熔断budgetCents 触顶抽奖继续，但只出"谢谢参与"

三层必须独立。如果只有"总开关"，出事时只能整站关闭，连公告都发不出去；如果只有"预算熔断"，前端仍显示"立即抽奖"，用户点了才发现全是谢谢参与，投诉更多。

3.2 分桶必须稳定 ​

ts
// 原型：activity-h5-demo/src/core/campaign.ts
export function grayBucket(campaignId: string, userId: string): number {
  const input = `${campaignId}:${userId}`;
  let hash = 0x811c9dc5;
  for (let i = 0; i < input.length; i += 1) {
    hash ^= input.charCodeAt(i);
    hash = Math.imul(hash, 0x01000193);
  }
  return Math.abs(hash) % 100;
}

3.3 上线检查单 ​

  • [ ] 备案与 HTTPS：域名已备案，证书链完整，http 强制跳 https；
  • [ ] 安全域名：微信 JS 安全域名、支付/分享相关域名已配置；
  • [ ] CDN：静态资源命中率与回源策略确认，index.html 不缓存、带 hash 资源长缓存；
  • [ ] 环境配置：测试 / 预发 / 生产三套 VITE_API_BASE 不串；
  • [ ] 灰度：grayPercent 从 5 → 20 → 50 → 100，每档观察至少 30 分钟；
  • [ ] 监控：接口错误率、抽奖成功率、库存余量、预算消耗四条告警；
  • [ ] 回滚：静态资源保留上一版本，配置中心能一键回退，DB 变更可逆；
  • [ ] 应急预案：奖品发错 / 库存超发 / 接口打挂，三种场景各自的止血动作与负责人；
  • [ ] 客服 FAQ：活动规则、奖品发放时间、异常处理口径；
  • [ ] 合规：隐私政策、活动规则、未成年人提示三个链接可访问。

3.4 回滚不是"撤销" ​

必须提前想清楚哪些操作不可逆：

操作可逆性回滚方式
静态资源发布可逆切回上一版 CDN 目录
配置开关可逆配置中心回退
库存扣减不可逆只能人工对账 + 补发/追回
优惠券已发放不可逆只能走作废流程
用户已分享的链接不可逆旧链接必须继续可用，不能 404

最后一条经常被忽略：活动结束后分享链接仍然在群里流传，旧链接至少要保持"活动已结束"页可访问，否则用户点开是 404，品牌损失比活动本身更大。

四、监控与漏斗：先定口径，再看曲线 ​

4.1 四条必须有的告警 ​

告警阈值示例说明
抽奖接口错误率5 分钟内 > 1%可能是库存/签名/发奖依赖故障
抽奖成功率骤降环比下降 > 30%常见于配置错误或活动提前结束
库存余量任一奖品 < 10%提前准备补货或降级
预算消耗速率超过日预算的 2 倍防刷或概率配置错误

阈值只是示例，真实值要按活动规模定。重点不是数字，而是每一条告警都对应一个明确的动作，否则就是噪音。

4.2 漏斗口径 ​

ts
// 原型：activity-h5-demo/src/core/tracking.ts
export function buildFunnel(events: ReadonlyArray<TrackingEvent>) {
  const steps: EventName[] = ['page_view', 'draw_click', 'draw_result', 'claim_click'];
  return steps.map(step => ({
    step,
    // 这里按 traceId 去重；真实看板按 userId 去重，两者不能混用
    users: new Set(events.filter(event => event.name === step).map(event => event.traceId)).size,
  }));
}

维度回答的问题常见错误

4.3 成本核算的最小公式 ​

text
单次抽奖期望成本 = Σ（奖品权重 / 10000 × 单件成本）
活动总成本       = 抽奖次数 × 单次期望成本 + 流量成本 + 人力成本
单个有效参与成本 = 活动总成本 / 去重参与人数

4.4 复盘文档写什么 ​

模块内容
目标 vs 实际立项时定的指标、实际值、差异原因
漏斗各步骤转化率、流失最大的环节
渠道各渠道 ROI、有效参与成本
成本奖品、流量、人力拆分
异常刷量、客诉、故障时间线
结论可复用的组件/策略、下次要改的三件事
归档配置快照、埋点事件表、海报模板、活动链接

"下次要改的三件事"必须具体到可执行，比如"把保底从 5 次改到 3 次并观察成本"，而不是"提升用户体验"。

五、合规：不能等法务最后一天才看 ​

活动页的合规风险集中在五处：

风险具体要求落到代码里
隐私收集手机号/地址前必须有隐私政策与授权表单前勾选，链接来自 legal.privacyUrl
抽奖合规明确活动规则、开奖方式、奖品数量与价值上限规则页 + legal.rulesUrl 必填
诱导分享不得"分享后才能抽奖"作为强制条件分享是加分项，不是门槛
广告法禁用"最""第一""国家级"等绝对化用语文案评审清单
未成年人需要监护人同意/提示legal.minorsNotice 展示

第 17 章把三个链接做成了必填字段，正是为了让合规从"文档要求"变成"发布阻断"。这条设计的价值在出事时才会体现：配置里没有链接，构建/启动自检直接报 error。

还有两条容易忽略：

  • 版权素材：主 KV、字体、BGM 都要有授权，活动结束后下架；
  • 数据安全：手机号、地址等个人信息加密存储，日志里不能打印明文。

六、资产沉淀：下一次活动应该更快 ​

一次活动做完，真正能复用的是这些：

资产原型对应位置复用方式
抽奖组件 / 状态机src/core/playMachine.ts换玩法只换事件与 UI
海报 SDKsrc/features/poster/布局纯函数 + 绘制薄层，换模板不动逻辑
埋点 SDKsrc/core/tracking.ts批量/重试/落盘机制与业务无关
风控中间件src/core/sign.ts、core/rateLimit.ts抽奖之外的接口也能挂
页面模板src/App.tsx + styles.css换 KV 与文案即可
看板模板buildFunnel + 指标定义口径固定，换活动只换数据源
测试矩阵tests/ 下的并发/幂等/降级用例新活动先跑一遍再改

判断"沉淀"是否成功的标准很朴素：下一次活动，上面这些文件能不能不改逻辑就复用。如果每个活动都要重写一遍库存扣减，那说明沉淀的是一份文档，不是代码。

七、关键点 ​

  1. 首屏优化先看产物：React 本体占大头，优化空间在"不加载什么"。
  2. 代码分割按能力拆，海报、排行榜这类重模块延迟加载。
  3. 构建目标降到 es2018，兼容老 WebView 的成本远低于线上白屏。
  4. 降级策略要有明确档位与"不做什么"，而不是一句"低端机降级"。
  5. 动画只用 transform / opacity，will-change 要克制。
  6. 弹窗层级要有统一阶梯，滚动穿透与键盘行为必须真机验证。
  7. 三层开关独立：总开关、灰度、奖品熔断。
  8. 灰度分桶算法不能变，扩量只改百分比。
  9. 回滚要考虑不可逆操作：库存、已发券、已分享的链接。
  10. 告警必须对应动作，否则就是噪音。
  11. 漏斗口径先写清楚：人次还是人数，直接影响复盘结论。
  12. 合规字段化，链接缺失即阻断发布。
  13. 资产沉淀的判据是"下次能不改逻辑复用"。

八、常见坑 ​

  1. 只优化业务代码：业务从 12KB 压到 8KB，vendor 还是 60KB，首屏没变化。
  2. 首屏加载海报模块：海报只在用户点"生成"时才需要，提前加载纯属浪费。
  3. target: 'esnext'：开发爽，老安卓 WebView 直接语法报错。
  4. 用 width/top 做动画：中低端机掉帧，用户以为卡死。
  5. will-change 满屏加：合成层过多，低内存机型闪退。
  6. 弹窗用 z-index: 99999：下次来个更高的，层级彻底失控。
  7. 只做总开关：出事只能全关，连公告都发不出去。
  8. 灰度扩量时换了哈希算法：已参与用户"掉出活动"。
  9. 把回滚理解成"撤销"：库存和已发券撤不回，只能对账。
  10. 活动结束后分享链接 404：群里流传的旧链接变成"页面不存在"。
  11. 告警没有动作：每天 200 条告警，最后没人看。
  12. 复盘只写"效果不错"：没有漏斗、没有成本、没有下次要改的三件事。
  13. 合规等法务最后一天看：改文案、改流程都来不及。

  • 第 05 章的状态管理，在活动页变成"不能出现非法中间态"的状态机；
