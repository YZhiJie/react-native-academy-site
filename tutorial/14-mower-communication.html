教程 14 · 割草机器人通信底座：MQTT、二进制帧与连接状态机 ​

目标：从零搭起一条"手机 → broker → 割草机"的可靠链路，做到断网不丢指令、弱网能降级、收发可解释。 版本锚点：React Native 0.87.1 + React 19.2.3 + TypeScript 严格模式；原型工程 mower-console-demo（与本站同级，独立于本仓库）。 前置：09 · 离线能力 的 outbox 思路、11 · 离线可靠性 的故障注入方法。本章把"业务数据同步"换成"设备控制指令"，可靠性要求更高一档。

前 13 章处理的是"内容和数据"：页面、导航、存储、离线、一致性、发布。到了割草机器人终端，问题换了一个形状：

  • 对端不是 HTTP 服务，而是一台会掉线、会没电、会开进信号盲区的机器；
  • 指令不是"晚点同步也行"，急停晚 3 秒就是事故；
  • 链路不是"通了/没通"两态，而是"MQTT 还连着但遥测已经停了"这种半死状态。

本章先解决通信底座。地图、轨迹、路径规划在 15 和 16 继续。

一、先把链路画清楚 ​

一条控制指令从点击"启动割草"到车端执行，实际经过四层：

层负责不负责原型文件
UI展示状态、收集输入、禁用危险操作不碰 socket，不判断重连src/ui/screens/*
编排何时重连、何时重放、何时降级不拼 MQTT 字节src/services/mqttService.ts
协议MQTT 3.1.1 报文编解码、QoS1、心跳不决定业务语义src/core/mqtt/codec.ts、client.ts
业务帧magic / 命令字 / seq / CRC16不关心传输是否 WebSocketsrc/core/protocol/frame.ts

分层的判据不是"代码放在哪个文件夹"，而是换掉一层时，另一层要不要改。例如把 WebSocket 换成原生 TCP，MqttClient 只换 transport；把 JSON 指令换成二进制帧，MqttService 的 outbox 逻辑不用动。

1.1 Topic 设计先定死 ​

原型只用一台车 mower-01，但 topic 已经按"多车"设计：

text
mower/{mowerId}/telemetry   位姿 / 电量 / 作业状态     车 → App   QoS1
mower/{mowerId}/nmea        RTK 的 NMEA 原文           车 → App   QoS0
mower/{mowerId}/cmd         JSON 控制指令               App → 车   QoS1
mower/{mowerId}/cmd/ack     车端业务 ACK               车 → App   QoS1
mower/{mowerId}/frame/down  二进制控制帧                App → 车   QoS1
mower/{mowerId}/frame/up    二进制应答帧                车 → App   QoS0
mower/{mowerId}/lwt         遗嘱消息（在线/失联）       车 → App   QoS1 + retain

两条经验：

  1. 遥测和 NMEA 分开。遥测要 QoS1，NMEA 是高频文本，丢了下一句就来，QoS0 更合适。把两者塞进一个 topic，等于让所有消息都付 QoS1 的成本。
  2. 业务 ACK 单独一个 topic。MQTT 的 PUBACK 只证明"broker 收到了"，不证明"车端执行了"。这两个语义必须分开，否则 UI 会把"已送达 broker"误显示成"已执行"。

二、最小可跑：broker、模拟车、RN 接入 ​

2.1 本地 broker：为什么用 aedes ​

生产环境推荐 mosquitto / EMQX，但本机没有 mosquitto，且我们要验证的只是"QoS1 / 遗嘱 / keepalive 的协议行为"，纯 Node 的 aedes 足够等价。

ts
// 原型：mower-console-demo/simulator/broker.ts
import { createServer } from 'node:net';
import { Aedes } from 'aedes';
import { WebSocketServer, createWebSocketStream } from 'ws';

const TCP_PORT = 1883; // 标准 MQTT/TCP，给命令行工具备用
const WS_PORT = 8888;  // MQTT over WebSocket，RN 端使用

const aedes = await Aedes.createBroker({
  heartbeatInterval: 30_000,
  connectTimeout: 15_000,
});

// 标准 TCP 监听：mosquitto_pub / mosquitto_sub 可以直接连
const tcpServer = createServer(aedes.handle);
tcpServer.listen(TCP_PORT);

// WebSocket 监听：把 ws 流适配成 aedes 需要的 duplex stream
const wsServer = new WebSocketServer({ port: WS_PORT });
wsServer.on('connection', socket => {
  aedes.handle(createWebSocketStream(socket));
});

2.2 模拟车端：遥测 + 遗嘱 ​

模拟车扮演"固件 + 4G 模组"，每 500ms 上报位姿，每 1s 吐一条 NMEA，并订阅控制指令。

ts
// 原型：mower-console-demo/simulator/mower.ts
const client = mqtt.connect(BROKER_URL, {
  clientId: `mower-node-${MOWER_ID}`,
  clean: true,
  keepalive: 20,
  reconnectPeriod: 1000,
  will: {
    topic: topic('lwt'),
    // 异常断线时由 broker 代发；retain 让后连上的 App 也能立刻看到"机器失联"
    payload: JSON.stringify({ online: false, reason: 'unexpected-disconnect', at: Date.now() }),
    qos: 1,
    retain: true,
  },
});

client.on('connect', () => {
  client.subscribe([topic('cmd'), topic('frame/down')], { qos: 1 });
  // 上线时主动发一条 online=true，覆盖上一次遗留的 retain 遗嘱
  client.publish(topic('lwt'), JSON.stringify({ online: true, at: Date.now() }), {
    qos: 1,
    retain: true,
  });
});

2.3 RN 端：手写一个最小 MQTT 客户端 ​

直接用 mqtt npm 包也能跑，但岗位要的是"看得懂协议"。原型手写了 CONNECT / SUBSCRIBE / PUBLISH / PUBACK / PINGREQ 五个报文：

ts
// 原型：mower-console-demo/src/core/mqtt/codec.ts
export function encodeConnect(options: ConnectOptions): Uint8Array {
  const clean = options.cleanSession !== false;
  let flags = clean ? 0x02 : 0x00;
  if (options.will) {
    flags |= 0x04;                              // 有遗嘱
    flags |= (options.will.qos & 0x03) << 3;   // 遗嘱 QoS
    if (options.will.retain) flags |= 0x20;     // 遗嘱 retain
  }

  const body = new Writer()
    .str('MQTT')
    .u8(4)                       // 协议级别 4 = MQTT 3.1.1
    .u8(flags)
    .u16(options.keepaliveSec)   // 心跳周期，秒
    .str(options.clientId);

  if (options.will) {
    body.str(options.will.topic);
    body.binary(typeof options.will.payload === 'string'
      ? encodeUtf8(options.will.payload)
      : options.will.payload);
  }
  return packet(MqttPacketType.CONNECT, 0, body.toBytes());
}

流式解码同样重要：WebSocket 一次 message 可能拿到半个 MQTT 报文，也可能拿到三个。decodePackets 返回 { packets, rest }，把未收全的尾巴留给下一次：

ts
// 原型：mower-console-demo/src/core/mqtt/codec.ts
export function decodePackets(buffer: Uint8Array): { packets: MqttPacket[]; rest: Uint8Array } {
  const packets: MqttPacket[] = [];
  let offset = 0;

  while (offset < buffer.length) {
    if (offset + 1 >= buffer.length) break;
    const first = buffer[offset];
    const packetType = first >> 4;
    const lengthInfo = readVarint(buffer, offset + 1);
    if (!lengthInfo) break;                       // 剩余长度都没收全
    const bodyStart = offset + 1 + lengthInfo.bytes;
    const bodyEnd = bodyStart + lengthInfo.value;
    if (bodyEnd > buffer.length) break;           // 报文未收全，保留到下次

    const body = buffer.subarray(bodyStart, bodyEnd);
    // ...按 packetType 分发
    offset = bodyEnd;
  }

  return { packets, rest: buffer.subarray(offset) };
}

三、QoS1、遗嘱、keepalive 各自保证什么 ​

这三个词经常被混着说，实际是三件不同的事：

机制保证不保证典型误用
QoS1broker 至少收到一次（PUBACK）车端执行、业务成功把 PUBACK 当"已执行"
遗嘱 LWTbroker 检测到异常断开时代发一条消息正常关机、App 主动断开也会触发（取决于实现）用 LWT 判断"任务完成"
keepalive双方在无业务数据时仍能发现死链应用层卡死、遥测停更只靠 keepalive 判断"车还能控制"

3.1 QoS1 的 PUBACK 必须有超时 ​

这是原型里真实修过的 bug。publishQos1 最初只 await PUBACK，没有超时：

ts
// 原型：mower-console-demo/src/core/mqtt/client.ts
publishQos1(topic: string, payload: string | Uint8Array): Promise<void> {
  const packetId = this.allocatePacketId();
  const timeoutMs = this.options.publishTimeoutMs ?? 5000;
  return new Promise<void>((resolve, reject) => {
    // 没有 PUBACK 超时，pump 会永远卡在第一条消息上：
    // 丢包场景下这不是"慢"，而是"队列彻底不动"。超时后交给 outbox 重发。
    const timer = setTimeout(() => {
      const pending = this.pendingQos1.get(packetId);
      if (!pending) return;
      this.pendingQos1.delete(packetId);
      pending.reject(new Error('PUBACK 超时'));
    }, timeoutMs);

    this.pendingQos1.set(packetId, { resolve, reject, topic, timer });
    this.socket?.send(encodePublish({ topic, payload, qos: 1, packetId }) as unknown as ArrayBuffer);
  });
}

为什么这很严重：发送循环是串行的，第一条等不到 PUBACK，后面所有指令（包括急停）都排在它后面。弱网下"慢"和"死"看起来一样，必须用超时把"死"显式化。

3.2 keepalive 之外还要有遥测看门狗 ​

keepalive 只能发现"TCP 层没数据"，发现不了"MQTT 还活着，但车端业务卡死"。所以状态机额外维护一个 lastTelemetryAt：

ts
// 原型：mower-console-demo/src/services/mqttService.ts
private watchdog(): void {
  const now = Date.now();
  const age = this.snapshot.state === 'connected' || this.snapshot.state === 'degraded'
    ? now - this.lastTelemetryAt
    : 0;
  this.store.set({ telemetryAgeMs: age });

  if (this.snapshot.state === 'connected' && age > TELEMETRY_STALE_MS) {
    this.dispatch({ type: 'TELEMETRY_STALE', now });
    this.store.log('warn', `遥测 ${age}ms 未更新，链路降级`);
  }
}

四、二进制帧：magic / 长度 / 命令字 / payload / CRC16 ​

MQTT 的 payload 是"不透明字节"，协议本身不关心内容。下位机为了省 RAM 和 CPU，通常不用 JSON，而是固定头 + CRC 的紧凑帧。

4.1 帧格式 ​

text
偏移   长度   字段
0      2      magic      0x4D 0x57（'M''W'）
2      1      version    0x01
3      1      cmd        命令字
4      1      flags      0x01 需 ACK / 0x02 应答 / 0x04 错误应答
5      1      reserved   必须为 0
6      2      seq        序号（0..65535 循环）
8      2      length     payload 长度（0..4096）
10     N      payload
末尾   2      crc16      CRC16/CCITT-FALSE，覆盖 magic..payload

几个设计取舍值得讲清楚：

  • CRC 放末尾而不是头里：流式解码可以"先读长度、再等 CRC"，不需要回退游标。
  • 长度上限 4096：超过就丢，避免恶意长度把内存打爆。
  • 版本号独立：将来换帧结构，旧固件可以按版本拒收，而不是误解码。
ts
// 原型：mower-console-demo/src/core/protocol/frame.ts
export function encodeFrame(frame: Frame): Uint8Array {
  const total = FRAME_HEADER_SIZE + frame.payload.length + FRAME_CRC_SIZE;
  const out = new Uint8Array(total);
  out[0] = FRAME_MAGIC_0; // 'M'
  out[1] = FRAME_MAGIC_1; // 'W'
  out[2] = frame.version;
  out[3] = frame.cmd;
  out[4] = frame.flags;
  out[5] = 0;             // reserved
  writeU16BE(out, 6, frame.seq);
  writeU16BE(out, 8, frame.payload.length);
  out.set(frame.payload, FRAME_HEADER_SIZE);

  // CRC 覆盖 magic..payload，不包含末尾两个 CRC 字节
  const checksum = crc16(out, 0, total - FRAME_CRC_SIZE);
  writeU16BE(out, total - FRAME_CRC_SIZE, checksum);
  return out;
}

4.2 流式解码：串口和 TCP 都会粘包/半包 ​

这是二进制协议最容易写错的地方。不能假设"一次 read = 一个帧"：

ts
// 原型：mower-console-demo/src/core/protocol/frame.ts
export class FrameStreamDecoder {
  private buffer: Uint8Array = new Uint8Array(0);

  feed(chunk: Uint8Array): Frame[] {
    this.buffer = concatBytes(this.buffer, chunk);
    const frames: Frame[] = [];

    while (true) {
      // 1. 对齐帧头：允许前面有噪声字节，逐字节丢弃
      const magicIndex = findMagic(this.buffer);
      if (magicIndex < 0) {
        // 保留最后 1 字节，避免 magic 恰好被拆到两次 feed 之间
        if (this.buffer.length > 1) this.buffer = this.buffer.slice(this.buffer.length - 1);
        break;
      }
      if (magicIndex > 0) this.buffer = this.buffer.slice(magicIndex);

      // 2. 头都没收齐就等下一次 feed
      if (this.buffer.length < FRAME_HEADER_SIZE) break;

      const payloadLength = readU16BE(this.buffer, 8);
      if (payloadLength > MAX_PAYLOAD_SIZE) {
        this.buffer = this.buffer.slice(2); // 跳过 magic，继续找下一帧
        continue;
      }

      const total = FRAME_HEADER_SIZE + payloadLength + FRAME_CRC_SIZE;
      if (this.buffer.length < total) break; // 半包，等下一段

      const expected = readU16BE(this.buffer, total - FRAME_CRC_SIZE);
      const actual = crc16(this.buffer, 0, total - FRAME_CRC_SIZE);
      if (expected !== actual) {
        // CRC 错不能整段丢弃：可能只是头部被噪声污染，跳过 magic 继续找
        this.buffer = this.buffer.slice(2);
        continue;
      }

      frames.push({
        version: this.buffer[2],
        cmd: this.buffer[3],
        flags: this.buffer[4],
        seq: readU16BE(this.buffer, 6),
        payload: this.buffer.slice(FRAME_HEADER_SIZE, FRAME_HEADER_SIZE + payloadLength),
      });
      this.buffer = this.buffer.slice(total);
    }

    return frames;
  }
}

三个细节：

  1. 没找到 magic 时保留 1 字节，否则 magic 被拆在两次 feed 之间就永远对不上。
  2. CRC 错时只跳过 2 字节，而不是丢掉整帧。噪声可能只污染了头部，后面还可能有一个好帧。
  3. 缓冲区上限保护：持续无帧头时不能无限增长。

五、连接状态机：五个状态，而不是一个布尔值 ​

isConnected 不够用，因为割草机有五种真实处境：

状态含义UI 允许的动作
idle从未连接 / 用户主动断开显示"连接"
connecting正在握手，等 CONNACK禁止重复点击
connected心跳和遥测都正常允许下发指令
degradedMQTT 还连着，但遥测超时只读遥测，禁止"启动割草"
reconnecting已断开，按退避重试指令进离线队列

状态机写成纯函数 reducer，输入 (snapshot, event)，输出新 snapshot，不碰定时器、不碰网络：

ts
// 原型：mower-console-demo/src/core/net/connectionMachine.ts
export function reduceConnection(
  snapshot: ConnectionSnapshot,
  event: ConnectionEvent,
  options: MachineOptions = {},
): ConnectionSnapshot {
  const now = event.now;

  switch (event.type) {
    case 'CONNECT_REQUESTED': {
      // 已在 connecting 时忽略重复点击，避免制造并行连接
      if (snapshot.state === 'connecting') return snapshot;
      return transition(snapshot, 'connecting', now, '用户发起连接', { attempt: 0 }, options);
    }

    case 'CONNACK_OK': {
      if (snapshot.state !== 'connecting' && snapshot.state !== 'reconnecting') return snapshot;
      return transition(snapshot, 'connected', now, 'MQTT CONNACK 成功', { attempt: 0 }, options);
    }

    case 'PING_TIMEOUT': {
      if (snapshot.state !== 'connected' && snapshot.state !== 'degraded') return snapshot;
      return scheduleReconnect(snapshot, now, '心跳超时：PINGRESP 未在阈值内返回', options);
    }

    case 'SOCKET_CLOSED': {
      // 已经在重连等待中时，旧的 socket 关闭事件不应重置退避计时器
      if (snapshot.state === 'idle' || snapshot.state === 'reconnecting') return snapshot;
      return scheduleReconnect(snapshot, now, event.reason, options);
    }

    case 'TELEMETRY_STALE': {
      if (snapshot.state !== 'connected') return snapshot;
      return transition(snapshot, 'degraded', now, '遥测超时，链路降级', {
        lastError: '位姿遥测超过阈值未更新',
      }, options);
    }

    case 'RETRY_DUE': {
      if (snapshot.state !== 'reconnecting') return snapshot;
      if (snapshot.nextRetryAt !== null && now < snapshot.nextRetryAt) return snapshot;
      return transition(snapshot, 'connecting', now, `第 ${snapshot.attempt + 1} 次重连`, options);
    }

    default:
      return snapshot;
  }
}

5.1 指数退避 + 全抖动 ​

ts
// 原型：mower-console-demo/src/core/net/backoff.ts
export function computeBackoff(
  attempt: number,
  options: BackoffOptions = {},
  random: () => number = Math.random,
): BackoffStep {
  const baseMs = options.baseMs ?? 500;
  const maxMs = options.maxMs ?? 30_000;
  const jitter = options.jitter ?? 1;
  const safeAttempt = Math.max(0, Math.min(20, Math.floor(attempt)));
  const ceilingMs = Math.min(maxMs, baseMs * 2 ** safeAttempt);
  // 全抖动：把等待摊到 [0, ceiling)，避免几十台设备同毫秒重连打尖峰
  const jittered = ceilingMs * (1 - jitter) + ceilingMs * jitter * random();
  return { attempt: safeAttempt, delayMs: Math.max(0, Math.round(jittered)), ceilingMs };
}

六、离线队列：幂等键比重试次数更重要 ​

断网时指令不能丢，重连后要重放。但"至少一次"重放会带来重复执行——割草机收到两条"启动"不是小事。解法是客户端生成幂等键，车端按键去重。

ts
// 原型：mower-console-demo/src/core/net/outbox.ts
async enqueue(input: EnqueueInput, now = Date.now()): Promise<OutboxRecord> {
  this.ensureLoaded();
  this.seq += 1;
  const id = `${now.toString(36)}-${this.seq.toString(36)}`;
  const record: OutboxRecord = {
    id,
    topic: input.topic,
    payload: input.payload,
    qos: input.qos ?? 1,
    // 重连重放时键不变，车端才能把 at-least-once 收敛成 effectively-once
    idempotencyKey: input.idempotencyKey ?? `${this.clientId}:${this.seq}`,
    createdAt: now,
    attempts: 0,
    nextAttemptAt: now,
    status: 'pending',
  };
  this.records.push(record);
  await this.persist();
  return { ...record };
}

6.1 重连时 inflight 必须一起放行 ​

原型里修过的另一个 bug：releaseAll 最初只把 pending 设为可发送，inflight 继续留着。结果断链前最后一条已经 claim 但没收到 ACK 的指令永远卡在 inflight，claimNext 永远跳过它。

ts
// 原型：mower-console-demo/src/core/net/outbox.ts
async releaseAll(now = Date.now()): Promise<number> {
  let released = 0;
  for (const record of this.records) {
    // inflight 必须一起放行：没有收到 ACK 的消息状态未知，
    // 必须允许重放，由幂等键兜底
    if (record.status === 'pending' || record.status === 'inflight') {
      record.status = 'pending';
      record.nextAttemptAt = now;
      released += 1;
    }
  }
  this.stats.replayed += released;
  await this.persist();
  return released;
}

// 原型：mower-console-demo/src/services/mqttService.ts
private scheduleFlush(): void {
  if (this.disposed || this.flushTimer) return;
  const next = this.outbox.nextPendingAt();
  if (next === null) return;
  const delay = Math.max(50, Math.min(30_000, next - Date.now()));
  this.flushTimer = setTimeout(() => {
    this.flushTimer = null;
    void this.flush();
  }, delay);
}

八、关键点 ​

  1. 协议分层按"换一层要不要改另一层"判断，不是按文件夹。
  2. QoS1 ≠ 业务成功。PUBACK 只到 broker，车端 ACK 才代表执行。
  3. 遗嘱消息由 broker 代发，App 自己断线时收不到任何消息。
  4. 二进制帧必须流式解码，半包、粘包、噪声、CRC 错都要有明确处理。
  5. 状态机用纯函数，所有分支可以在 Node 里穷举，不用等真实超时。
  6. 幂等键由客户端生成并持久化，网络层的 at-least-once 才能收敛成 effectively-once。
  7. 退避要有上限和抖动，否则长时间断网会"睡死"，同时重连会打尖峰。

九、常见坑 ​

  1. 主动关闭被"迟到旧 socket"守卫吞掉：destroy() 先把 this.socket 置空再 close()，onclose 里的守卫会把这个事件当成旧 socket 忽略。结果是心跳超时后状态机永久停在 connected。修法是 destroy(reason, notify = true) 显式通知上层。
  2. publishQos1 没有 PUBACK 超时：丢包时发送队列永久阻塞，后面的急停也发不出去。
  3. releaseAll 只放行 pending：inflight 记录永久卡死，重连后看着"队列里有一条"，但永远不发。
  4. 把 claimNext() === null 当成队列空：忽略退避窗口，最后一条失败记录静默卡死。
  5. 只靠 keepalive 判断链路健康：MQTT 活着但遥测停更时，UI 仍然显示"在线"，用户会以为可以启动割草。
  6. 把 PUBACK 当业务 ACK：UI 显示"已执行"，实际车端可能根本没收到。
  7. 串口假设"一次 read 一个帧"：真实串口和 TCP 一样会半包/粘包。

十、验收清单 ​

  • [ ] broker 同时开 TCP 1883 与 WS 8888，RN 只走 WS；
