教程 17 · 活动 H5 工程骨架：从立项表到玩法状态机 ​

目标：把一份"活动立项表"翻译成可校验的运行时配置、一条不会出现矛盾中间态的玩法状态机，以及一套能解释数据的埋点与降级方案。 版本锚点：React 19.2.3 + TypeScript 5.9 严格模式 + Vite 7.1；同一套 React 叙事，不引入第二套框架。 前置：13 · 发布工程化与安全、10 · WebView 离线、05 · 状态管理。 原型：activity-h5-demo（与仓库同级的独立工程，不随本仓库入库）。

前 16 章都在回答"App 里怎么把一件事做对"。这一部分换一个战场：同一个团队要交付一个移动端活动 H5——周期两周、投放靠分享、预算有上限、出事要能一键停。

活动页看起来比 App 简单，实际上它把工程约束压缩到了极致：没有发版窗口，只能靠灰度与开关；流量在开奖瞬间脉冲式涌入；用户不给你第二次机会，首屏慢 1 秒就走。这一章先解决"骨架"，后面三章依次解决"钱与风控""传播""上线与复盘"。

先对齐整条链路的章节归属，再往下读：

一、立项表不是文案，是配置契约 ​

立项会上通常会写下这几行：活动目标、核心指标、预算、周期、目标用户、投放渠道、竞品调研、活动方案、法务合规。

其中只有一部分能变成代码里的字段。分不清这一点，就会出现两种事故：把"提升品牌好感"写成 KPI 却无法埋点，以及预算只是个数字，没有任何代码拦住超支。

1.1 能落成类型的那一半 ​

ts
// 原型：activity-h5-demo/src/core/campaign.ts

几个刻意的设计：

  • 金额一律用"分"的整数。用浮点存钱，迟早会出现 0.1 + 0.2 的对账差异。
  • 权重用万分比整数（20 表示 0.20%）。小数权重在求和时会漂移，还无法精确断言"加起来等于 100%"。
  • 合规链接是必填字段，不是文档里的一句话。字段缺失就发布失败，这是唯一能让合规真正生效的方式。
  • grayPercent 与 drawEnabled 放在配置里，而不是写死在代码里。活动出问题时，运营要能在不发版的情况下止血。

至于"品牌好感""用户心智"这类目标，不该塞进这个类型。它们应该留在复盘文档里，用定性材料回答——能被埋点验证的才配叫指标。

1.2 配置自检：构建期拦必然事故，启动期拦运行时问题 ​

ts
// 原型：activity-h5-demo/src/core/campaign.ts（节选）
export function validateCampaign(config: CampaignConfig, now = Date.now()): ConfigIssue[] {
  const issues: ConfigIssue[] = [];
  const push = (field: string, severity: ConfigIssue['severity'], message: string) => {
    issues.push({ field, severity, message });
  };

  if (config.startAt >= config.endAt) push('startAt', 'error', '开始时间必须早于结束时间');
  if (now > config.endAt) push('endAt', 'warn', '活动已结束，页面应进入"活动已结束"态');
  if (config.dailyDrawLimit > config.totalDrawLimit) {
    push('dailyDrawLimit', 'error', '每日次数不能大于总次数，否则规则自相矛盾');
  }
  if (!config.legal.privacyUrl || !config.legal.rulesUrl) {
    push('legal', 'error', '隐私政策与活动规则链接缺失，不允许上线');
  }

  const totalWeight = config.prizes.reduce((sum, prize) => sum + prize.weight, 0);
  if (totalWeight !== 10000) {
    // 用整数万分比而不是小数，就是为了能做这个精确校验
    push('prizes.weight', 'error', `奖品权重之和必须是 10000，当前 ${totalWeight}`);
  }

  // 最坏情况预算：所有有限库存全部发完要花多少钱
  const worstCaseCents = config.prizes.reduce((sum, prize) => {
    if (!Number.isFinite(prize.stock)) return sum;
    return sum + prize.stock * prize.unitCostCents;
  }, 0);
  if (worstCaseCents > config.budgetCents) {
    push('budgetCents', 'error', `库存全发完需 ${worstCaseCents} 分，超过预算 ${config.budgetCents} 分`);
  }

  return issues;
}

1.3 灰度分桶：同一用户必须稳定命中同一个桶 ​

ts
// 原型：activity-h5-demo/src/core/campaign.ts
export function grayBucket(campaignId: string, userId: string): number {
  const input = `${campaignId}:${userId}`;
  let hash = 0x811c9dc5;
  for (let i = 0; i < input.length; i += 1) {
    hash ^= input.charCodeAt(i);
    hash = Math.imul(hash, 0x01000193);
  }
  return Math.abs(hash) % 100;
}

二、页面结构：活动页只有一条主路径 ​

2.1 单页 + 阶段，而不是多路由 ​

活动 H5 的真实导航路径只有一条：进入 → 看到活动 → 抽 → 看结果 → 领 → 分享。

拆成 /index、/draw、/result、/share 四个路由会带来三个副作用：

  1. 每次跳转都可能触发一次页面级重载（微信 WebView 的回退尤其不可控）；
  2. 分享链接要携带"当前在哪一步"，参数一多就容易丢；
  3. 返回键的行为变成"回到哪一步"，而不是"关掉活动"。

所以原型只有一个入口 App.tsx，页面内的分支由状态机驱动。海报这类体积较大的模块用 React.lazy 拆出去——按能力拆分，而不是按路由拆分。

tsx
// 原型：activity-h5-demo/src/App.tsx（节选）
// 海报模块体积最大（布局 + 绘制 + 导出），单独成 chunk，点"生成海报"才加载
const PosterPanel = lazy(() => import('./features/poster/PosterPanel'));

interface Envelope {
  code: number;
  message: string;
  data?: unknown;
}

function sendJson(response: ServerResponse, status: number, body: Envelope): void {
  const payload = JSON.stringify(body);
  response.writeHead(status, {
    'content-type': 'application/json; charset=utf-8',
    'content-length': Buffer.byteLength(payload),
    // 活动接口一律不缓存，避免 CDN 把"抽奖结果"缓存给下一个人
    'cache-control': 'no-store',

  response.end(payload);
}

3.3 HTTP 状态码与业务码必须分层 ​

这是活动页最容易埋雷的地方：

层例子前端该怎么处理
HTTP 4xx/5xx401 签名失败、429 频控、500 服务异常网络/网关层问题，可以重试或提示稍后再试
业务码 code !== 040002 次数用完、40001 参数错误业务规则结果，不能重试
HTTP 200 + code = 0 + phase: ended活动结束展示结束态，不是错误

把"次数用完"实现成 HTTP 500，会导致前端把它归为"网络错误 → 自动重试 3 次"，白白打三次库存接口。原型里 DRAW_REJECTED 的 retryable 字段就是用来区分这两类失败的。

四、玩法状态机：五个中间态，别用布尔量拼 ​

4.1 为什么必须上状态机 ​

抽奖过程中真实存在的状态：

  1. 配置还没拉到（booting）
  2. 可以抽（idle）
  3. 请求发出去了，结果未知（drawing）
  4. 结果出来了，弹窗展示中（result）
  5. 领取中（claiming）／领取完成（claimed）
  6. 活动结束或被风控拦截（ended / blocked）

如果用 loading、showModal、hasResult、canDraw 四个布尔量拼，会产生 loading=true && hasResult=true 这种非法组合，然后你在渲染层写一堆 if 去猜"到底该显示什么"。

ts
// 原型：activity-h5-demo/src/core/playMachine.ts
export type PlayPhase =
  | 'booting' | 'idle' | 'drawing' | 'result'
  | 'claiming' | 'claimed' | 'ended' | 'blocked';

export interface PlayState {
  phase: PlayPhase;
  drawsLeft: number;
  lastResult: DrawResult | null;
  lastError: { code: string; message: string; retryable: boolean } | null;
  /** 当前在飞或待重试的请求 id；重试必须复用它，服务端才能幂等去重 */
  pendingRequestId: string | null;
}

4.2 reducer：把非法迁移直接吃掉 ​

ts
// 原型：activity-h5-demo/src/core/playMachine.ts（节选）
export function reducePlay(state: PlayState, event: PlayEvent): PlayState {
  switch (event.type) {
    case 'DRAW_TAP': {
      // 只有 idle 能起抽。drawing 时重复点击直接丢弃，这是最便宜的去重。
      if (state.phase !== 'idle') return state;
      if (state.drawsLeft <= 0) {
        return { ...state, phase: 'blocked', lastError: { code: 'DRAW_LIMIT', message: '今日次数已用完', retryable: false } };
      }
      // 上一次失败后要求复用同一个 requestId；换了 id 说明调用方绕过了幂等通道
      if (state.pendingRequestId !== null && state.pendingRequestId !== event.requestId) {
        return state;
      }
      return { ...state, phase: 'drawing', lastError: null, pendingRequestId: event.requestId };
    }

    case 'DRAW_ACK': {
      // 迟到的重复响应（网络重传、双通道回包）不应覆盖已有结果
      if (state.phase !== 'drawing') return state;
      return { ...state, phase: 'result', drawsLeft: Math.max(0, event.drawsLeft), lastResult: event.result, pendingRequestId: null };
    }

    case 'DRAW_REJECTED': {
      if (state.phase !== 'drawing') return state;
      if (event.retryable) {
        // 网络类失败：回到 idle，但保留 requestId，下一次点击必须复用它
        return { ...state, phase: 'idle', lastError: { code: event.code, message: event.message, retryable: true } };
      }
      return { ...state, phase: 'blocked', lastError: { code: event.code, message: event.message, retryable: false }, pendingRequestId: null };
    }
    // ...
  }
}

4.4 纯函数的成本 ​

reducePlay 在 Node 24 / V8 上的基准（50 万次迁移循环，含 DRAW_TAP → DRAW_ACK → DISMISS）：

函数耗时单次
reducePlay32.1 ms / 50 万次0.06 µs
decideDraw（第 18 章）77.8 ms / 50 万次0.16 µs

对活动页来说，这两者都可以忽略不计。状态机的价值不在性能，而在于它让"不可能的状态"无法被表达。这个数字的边界：跑在 Node/V8，不是 Hermes；但纯 reducer 没有平台 API 依赖，量级差异不影响结论。

5.2 批量、重试、落盘：三个机制缺一不可 ​

ts
// 原型：activity-h5-demo/src/core/tracking.ts（节选）
track(name: EventName, traceId: string, props = {}): void {
  this.queue.push({ name, traceId, ts: this.now(), props });
  if (this.queue.length >= this.flushSize) {
    void this.flush();
    return;
  }
  if (!this.timer) {
    this.timer = setTimeout(() => {
      this.timer = null;
      void this.flush();
    }, this.flushIntervalMs);
  }
}

/** 页面隐藏 / 卸载时调用：用同步兜底，别让数据跟着页面一起消失 */
flushOnHide(): TrackingEvent[] {
  if (this.timer) {
    clearTimeout(this.timer);
    this.timer = null;
  }
  const pending = this.queue;
  this.queue = [];
  if (pending.length > 0) this.options.persist?.(pending);
  return pending;
}

5.3 漏斗口径先写清楚，再写 SQL ​

export function buildFunnel(events: ReadonlyArray<TrackingEvent>) {
  const steps: EventName[] = ['page_view', 'draw_click', 'draw_result', 'claim_click'];
  return steps.map(step => ({
    step,
    // 这里按 traceId 去重；真实看板按 userId 去重，两者不能混用
    users: new Set(events.filter(event => event.name === step).map(event => event.traceId)).size,
  }));
}

6.1 四组信号，三档策略 ​

    case 'low':

export function pickImages(
  candidates: ReadonlyArray<ImageCandidate>,
  policy: DegradePolicy,
  supportsWebp: boolean,
): ImageCandidate[] {
  return candidates
    .filter(image => (image.format === 'webp' ? supportsWebp : true))
    .filter(image => image.sizeKB <= policy.imageBudgetKB)
    .sort((left, right) => left.sizeKB - right.sizeKB)
    .slice(0, policy.preloadImages);
}

七、关键点 ​

  1. 立项表必须能翻译成字段，翻不进去的目标不叫指标。预算是字段，不是一句"控制在 X 万以内"。
  2. 金额用分、权重用万分比，整数才能做精确校验与对账。
  3. 配置自检分两层：构建期拦"权重不平""预算不够"，启动期拦"活动过期""未开灰度"。
  4. 灰度分桶必须稳定，哈希输入里要带 campaignId，否则同一用户在两个活动间会串桶。
  5. 活动页是一条主路径，用状态机而不是路由来表达"抽到哪一步"。
  6. 非法事件返回原引用，这是最便宜的"测试友好"设计。
  7. requestId 跨重试保持不变，这是服务端幂等成立的前提。
  8. HTTP 码与业务码分层，否则前端会把"次数用完"当网络错误自动重试。
  9. 埋点要带 traceId，且漏斗口径要提前定义是"人次"还是"人数"。
  10. 降级靠能力探测，先砍装饰与图片，最后才动主流程。

八、常见坑 ​

  1. 把预算写成文案：配置里只有 budgetCents 而没有 unitCostCents，超支时才发现算不出花了多少钱。
  2. 用浮点存概率：0.001 + 0.003 + ... 加起来不等于 1，最后一档永远抽不到。
  3. 每日次数与总次数互相矛盾：dailyDrawLimit = 5、totalDrawLimit = 3，用户永远抽不满。
  4. 骨架屏尺寸和真实布局不一致：内容到位时页面抖动，用户误以为点错按钮。
  5. 只加 viewport-fit=cover 却没写 env()（或反过来），安全区代码形同虚设。
  6. 把抽奖结果缓存在 CDN：接口没设 no-store，第二个用户看到了第一个人的中奖记录。
  7. 用 Math.random() 当请求 id 且每次点击重新生成：超时重试直接变成二次扣次数。
  8. 埋点上报阻塞在点击回调里：网络差时按钮 2 秒没反应，用户开始连点。
  9. 省流量模式只降一档：用户主动表达了"网络贵"，还给他加载 Lottie，体验与成本双输。
  10. 认为灰度开关能替代回滚：开关只能关掉抽奖入口，已经发出去的奖品收不回来。

九、验收清单 ​

  • [ ] 立项表的每个目标都能对应到字段或复盘材料，没有"悬空 KPI"；
  • [ ] 金额字段单位为分，权重为万分比且总和精确等于 10000；
  • [ ] 构建期与启动期都会跑 validateCampaign，error 级问题阻断发布；
  • [ ] 灰度基于 campaignId + userId 稳定哈希，刷新不闪变；
  • [ ] 页面只有一条主路径，海报等重模块按需加载；
  • [ ] 骨架屏尺寸与真实布局一致；
  • [ ] viewport-fit=cover 与 env(safe-area-inset-*) 成对出现；
  • [ ] 接口清单包含幂等键与错误码分层说明；
  • [ ] 状态机覆盖 booting / idle / drawing / result / claiming / claimed / ended / blocked；
  • [ ] 重试必须复用 requestId，并有单测守护；
  • [ ] 埋点批量 + 重试 + 落盘三件套齐全，漏斗口径写进文档；
  • [ ] 降级策略基于能力探测，且不依赖机型白名单。
