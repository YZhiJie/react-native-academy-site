教程 09 · 离线能力：本地存储、离线优先与数据同步 ​

目标：把 App 从"联网才能用"改造成"本地先写、联网再同步"，并给出可落地的最小实现。 版本锚点：React Native 0.87.1（新架构 bridgeless + Hermes）、React 19.2.3。 承接：05 · 状态管理 的 persist 只解决了"设置项不丢"；本章解决"业务数据在断网时仍然可用、可写、可回放"。

离线不是"加个缓存"这么简单。真正要回答的是三个问题：

  1. 断网时首屏拿什么渲染？ —— 本地快照，而不是空白页。
  2. 断网时的写操作去哪了？ —— 先落本地库，再进 outbox 队列等联网回放。
  3. 联网后怎么保证不重复、不乱序、不覆盖别人的修改？ —— 幂等键 + 版本号 + 冲突策略。

本章按这三条线给出最小实现。示例都是 TypeScript 严格模式、函数组件，代码可直接拆进 src/storage/ 与 src/sync/。

一、先画一张离线分层地图 ​

层放什么推荐工具生命周期
内存 store当前屏幕数据、UI 状态Zustand（05 章）随进程消失
KV 存储设置项、首屏快照、HTTP 缓存元数据AsyncStorage / MMKV随 App 卸载消失
关系库业务实体、outbox 队列、同步游标@op-engineering/op-sqlite随 App 卸载消失
文件离线包、导出文件、大图react-native-blob-util（10 章）需主动清理
图片缓存封面、头像原生图片库的磁盘缓存由系统/库淘汰

选型只看三件事：数据形状、读写频率、可靠性要求。

方案适合不适合关键差异
AsyncStorage小 JSON、设置项、低频读写高频写入、大对象、复杂查询异步 API；Android 端历史上对单条大 value 有游标窗口限制，大对象别塞进来
MMKV高频 KV、启动即读的配置需要事务/查询的结构化数据同步 API（本章包一层 Promise 统一接口）；v4 是 Nitro Module，必须搭配 react-native-nitro-modules
op-sqlite业务实体、outbox、需要索引/事务的数据纯 KV、超小数据JSI + codegen，同步 open()、异步 execute()，自带事务与参数绑定

分工边界（本章只讲这两层，不混用）：

  • 设置项、开关、首屏快照、缓存元数据 → KV（AsyncStorage 或 MMKV）。
  • 业务实体、outbox、同步游标、需要 WHERE / JOIN / 索引 的数据 → op-sqlite。
  • 不要把同一份数据同时写进 KV 和关系库；KV 只存"指针"和"快照"，事实源始终是关系库。

2.1 AsyncStorage 实现 ​

ts
// src/storage/asyncStorageStore.ts
import AsyncStorage from '@react-native-async-storage/async-storage';
import type { KeyValueStore } from './kv';

export const asyncStorageStore: KeyValueStore = {
  async get<T>(key: string): Promise<T | null> {
    const raw = await AsyncStorage.getItem(key);
    if (raw == null) return null;
    try {
      return JSON.parse(raw) as T;
    } catch {
      // 旧版本写入的脏数据不应该让 App 启动即崩：读失败就当没有
      await AsyncStorage.removeItem(key);
      return null;
    }
  },

  async set<T>(key: string, value: T): Promise<void> {
    await AsyncStorage.setItem(key, JSON.stringify(value));
  },

  async remove(key: string): Promise<void> {
    await AsyncStorage.removeItem(key);
  },

  async clear(): Promise<void> {
    await AsyncStorage.clear();
  },
};

2.2 MMKV 实现（同步 API 包成 Promise） ​

ts
// src/storage/mmkvStore.ts
import { createMMKV } from 'react-native-mmkv';
import type { KeyValueStore } from './kv';

// v4 用工厂函数；id 一旦上线就不要改：它对应磁盘上的独立存储目录
const mmkv = createMMKV({ id: 'app-kv' });

export const mmkvStore: KeyValueStore = {
  async get<T>(key: string): Promise<T | null> {
    const raw = mmkv.getString(key);
    if (raw == null) return null;
    try {
      return JSON.parse(raw) as T;
    } catch {
      mmkv.remove(key);
      return null;
    }
  },

  async set<T>(key: string, value: T): Promise<void> {
    // MMKV 原生类型只有 string/number/boolean/ArrayBuffer，对象统一按 JSON 字符串存
    mmkv.set(key, JSON.stringify(value));
  },

  async remove(key: string): Promise<void> {
    mmkv.remove(key);
  },

  async clear(): Promise<void> {
    mmkv.clearAll();
  },
};

常见坑 1：不要同时在 AsyncStorage 和 MMKV 里存同一份 key，双写迟早不一致。 常见坑 2：kv.clear() 会清掉登录态之外的所有缓存，登出时请用"按前缀删除"而不是全清。 常见坑 3：KV 只适合小对象。把列表、队列塞进 KV，会在数据量上来后变成全量读写 + 无索引扫描。

实测（2026-11-05，iPhone 17 / iOS 26.5 模拟器，MMKV 4.3.2）：

  • 同进程内用另一把 encryptionKey 再开同一个 id，仍能读到旧值（命中进程内缓存实例），不能据此判断"错 key 能解密"。
  • 跨进程：冷启动用 key1 打开 lab-cold 写入 cold-value → simctl terminate 强杀 → 冷启动用 key2 打开同一 id：getString('k') 返回 null、getAllKeys() 为 []、不抛错。
  • 密钥轮换同理：用新 key 打开 lab-rot，读不到旧值，也不抛错。

结论：MMKV 的错 key / 换 key 失败形态是静默读空，不是报错。判定必须用"能否解出预期值"，不能靠 try/catch；轮换必须先迁移，再切换 key。

三、关系库：op-sqlite 建库、迁移与事务 ​

3.1 打开数据库 ​

ts
// src/storage/db.ts
import { open, type DB, type QueryResult } from '@op-engineering/op-sqlite';

let db: DB | null = null;

/** op-sqlite 的 open() 是同步的；单例打开，避免重复连接 */
export function getDb(): DB {
  if (!db) {
    // 不传 location 时使用库默认沙盒目录（iOS / Android 各自由原生侧决定）
    db = open({ name: 'offline.db' });
  }
  return db;
}

/** 把 QueryResult.rows 转成业务类型；op-sqlite 的行是 Record<string, Scalar> */
export function rowsOf<T>(result: QueryResult): T[] {
  return result.rows as unknown as T[];
}

export type OutboxStatus = 'pending' | 'syncing' | 'failed';

export type OutboxRow = {
  id: string;
  entity: 'note';
  op: 'create' | 'update' | 'delete';

  idempotency_key: string;
  status: OutboxStatus;

3.2 schema 与版本化迁移 ​

ts
// src/storage/schema.ts
import { getDb } from './db';

async function schemaVersion(): Promise<number> {
  const result = await getDb().execute('PRAGMA user_version;');
  const row = result.rows[0];
  return Number(row?.user_version ?? 0);
}

export async function initDb(): Promise<void> {
  const db = getDb();

  // WAL：读写并发更稳，崩溃恢复能力更好
  await db.execute('PRAGMA journal_mode = WAL;');

  // 只做"向前迁移"：每个版本一个 if 块，永不回退 schema
  if (await schemaVersion() < 1) {
    await db.transaction(async tx => {
      await tx.execute(`
        CREATE TABLE IF NOT EXISTS notes (
          id         TEXT PRIMARY KEY NOT NULL,
          title      TEXT NOT NULL,
          body       TEXT NOT NULL,
          revision   INTEGER NOT NULL,
          dirty      INTEGER NOT NULL DEFAULT 0,
          updated_at INTEGER NOT NULL
        );
      `);

      await tx.execute(`
        CREATE TABLE IF NOT EXISTS outbox (
          id              TEXT PRIMARY KEY NOT NULL,
          entity          TEXT NOT NULL,
          op              TEXT NOT NULL,
          payload         TEXT NOT NULL,
          idempotency_key TEXT NOT NULL UNIQUE,
          status          TEXT NOT NULL DEFAULT 'pending',
          attempts        INTEGER NOT NULL DEFAULT 0,
          next_attempt_at INTEGER NOT NULL DEFAULT 0,
          locked_at       INTEGER NOT NULL DEFAULT 0,
          created_at      INTEGER NOT NULL
        );
      `);

      // 回放扫描只走 status + next_attempt_at，索引必须建
      await tx.execute(`
        CREATE INDEX IF NOT EXISTS idx_outbox_pending
        ON outbox (status, next_attempt_at);
      `);

      await tx.execute('PRAGMA user_version = 1;');
    });
  }

  // 后续版本示例：if (await schemaVersion() < 2) { ... user_version = 2 }
}

3.3 参数化查询与事务边界 ​

op-sqlite 用 ? 占位，参数数组按位置绑定，不要手拼 SQL：

ts
// ✅ 参数绑定：值会被转义，SQL 结构不被注入
await getDb().execute(
  'SELECT * FROM notes WHERE dirty = ? ORDER BY updated_at DESC',
  [1],
);

// ✅ 多表写入必须在同一个事务里，避免"业务表成功、队列表失败"
await db.transaction(async tx => {
  await tx.execute('UPDATE notes SET title = ? WHERE id = ?', [title, id]);
  await tx.execute('INSERT INTO outbox (...) VALUES (...)', [/* ... */]);
});

// ❌ 不要拼字符串：标题里一个引号就能把 SQL 结构打断
// await db.execute(`UPDATE notes SET title = '${title}' WHERE id = '${id}'`);

事务里能做：

  • 多条 INSERT / UPDATE / DELETE 原子提交；
  • 事务内读到自己未提交的写入；
  • 任何一条抛错 → 整个事务回滚。

事务里不要做：

  • fetch、文件下载、await 长时间操作（会占住 SQLite 连接）；
  • 跨库 ATTACH 的复杂写入（先拆成两段，各自事务）。

4.2 先写本地，再入队（同一个事务） ​

ts
// src/sync/outbox.ts
import { getDb } from '../storage/db';
import type { NoteInput } from './types';

/** 仅用于本地主键/幂等键拼装，不要用于安全场景 */
function makeClientId(): string {
  return `${Date.now().toString(36)}-${Math.random().toString(36).slice(2, 10)}`;
}

export async function enqueueNote(input: NoteInput): Promise<void> {
  const db = getDb();
  const now = Date.now();
  const id = makeClientId();

  // 幂等键 = 业务对象 + 业务版本：同一版本重复点击只会入队一次
  const idempotencyKey = `note:${input.noteId}:${input.revision}`;

  await db.transaction(async tx => {
    // ① 先落本地业务表（dirty=1 表示"有未同步改动"）
    await tx.execute(
      `INSERT OR REPLACE INTO notes
         (id, title, body, revision, dirty, updated_at)
       VALUES (?, ?, ?, ?, 1, ?)`,
      [input.noteId, input.title, input.body, input.revision, now],
    );

    // ② 同一次业务变更写入 outbox；UNIQUE 约束负责兜底防重
    await tx.execute(
      `INSERT OR IGNORE INTO outbox
         (id, entity, op, payload, idempotency_key, status, attempts, next_attempt_at, locked_at, created_at)
       VALUES (?, 'note', 'update', ?, ?, 'pending', 0, 0, 0, ?)`,
      [id, JSON.stringify(input), idempotencyKey, now],
    );
  });
}

4.3 回放：单飞、claim、限批、退避 ​

ts
// src/sync/drain.ts
import { getDb, rowsOf } from '../storage/db';
import type { OutboxRow } from '../storage/db';

const MAX_ATTEMPTS = 5;
let draining = false;

/**
 * 回放 outbox。
 * @param send 由调用方注入，方便测试时替换成假实现
 * @returns 本轮成功提交的条数
 */
export async function drainOutbox(send: (row: OutboxRow) => Promise<void>): Promise<number> {
  // 单飞：AppState 与 NetInfo 可能同时触发，绝不能并发回放
  if (draining) return 0;
  draining = true;

  const db = getDb();
  let done = 0;
  const now = Date.now();

  try {
    // 崩溃恢复：上一轮停在 syncing 超过 2 分钟的，重新放回 pending
    await db.execute(
      `UPDATE outbox SET status = 'pending', locked_at = 0
       WHERE status = 'syncing' AND locked_at < ?`,
      [now - 120_000],
    );

    const result = await db.execute(
      `SELECT * FROM outbox
       WHERE status = 'pending' AND next_attempt_at <= ?
       ORDER BY created_at ASC
       LIMIT 20`,
      [now],
    );
    const batch = rowsOf<OutboxRow>(result);

    // 先在事务里整体 claim，避免两个触发点同时读到同一批 pending
    await db.transaction(async tx => {
      for (const row of batch) {
        await tx.execute(
          `UPDATE outbox SET status = 'syncing', locked_at = ?
           WHERE id = ? AND status = 'pending'`,
          [now, row.id],
        );
      }
    });

    for (const row of batch) {
      try {
        await send(row);
        // 成功即删：服务端已持久化，本地不再需要这条指令
        await db.execute('DELETE FROM outbox WHERE id = ?', [row.id]);
        done += 1;
      } catch {
        const attempts = row.attempts + 1;
        // 指数退避 + 抖动：1s、2s、4s…上限 5 分钟
        const delay = Math.min(300_000, 1_000 * 2 ** attempts) * (0.5 + Math.random());
        const status = attempts >= MAX_ATTEMPTS ? 'failed' : 'pending';
        await db.execute(
          `UPDATE outbox
           SET status = ?, attempts = ?, next_attempt_at = ?, locked_at = 0
           WHERE id = ?`,
          [status, attempts, Date.now() + Math.round(delay), row.id],
        );
      }
    }
  } finally {
    draining = false;
  }

  return done;
}

五、冲突解决：LWW 与服务端版本号 ​

离线写多了，冲突必然出现：同一份数据在手机 A 和手机 B 上都被改了。策略要提前定，不要等线上撞上再说。

策略规则适合风险
LWW（Last Write Wins）时间戳大者胜个人笔记、草稿、偏好设置设备时钟不准会误判
服务端版本号version 大者胜，本地有 dirty 时转人工大多数业务实体需要服务端维护版本
服务端权威以服务端返回为准，本地改动丢弃/重放库存、余额、名额用户体验差，需提示
CRDT / OT合并而非覆盖协同编辑实现成本高

推荐组合：服务端版本号作为主序，updatedAt 只做同版本时的兜底；金额、库存这类数据禁止 LWW。

ts
// src/sync/merge.ts
// T 换成你的业务实体即可；下文用 Note（定义见 9.1 的 homeSnapshot.ts）
export type RemoteRecord<T> = { data: T; version: number; updatedAt: number };
export type LocalRecord<T> = RemoteRecord<T> & { dirty: boolean };

export type MergeResult<T> =
  | { action: 'take-local' }
  | { action: 'take-remote'; record: LocalRecord<T> }
  | { action: 'conflict' };

export function mergeByVersion<T>(
  local: LocalRecord<T>,
  remote: RemoteRecord<T>,
): MergeResult<T> {
  // ① 服务端版本更高：正常情况下应接受远端
  if (remote.version > local.version) {
    // 但本地还有未提交改动 → 不静默覆盖，交给业务层处理
    if (local.dirty) return { action: 'conflict' };
    return { action: 'take-remote', record: { ...remote, dirty: false } };
  }

  // ② 版本相同：用 updatedAt 做 LWW 兜底（时钟不同步时只是退化策略）
  if (remote.version === local.version) {
    if (!local.dirty && remote.updatedAt > local.updatedAt) {
      return { action: 'take-remote', record: { ...remote, dirty: false } };
    }
    return { action: 'take-local' };
  }

  // ③ 本地版本更高：保留本地，等待回放
  return { action: 'take-local' };
}

6.1 带 ETag 的 GET 缓存 ​

ts
// src/net/cachedGet.ts
import { kv } from '../storage';
import { HttpError } from '../sync/send';

type CacheEntry<T> = {
  data: T;
  etag: string | null;
  savedAt: number;
};

export async function cachedGet<T>(url: string, ttlMs: number): Promise<T> {
  const key = `http:${url}`;
  const cached = await kv.get<CacheEntry<T>>(key);

  // ① 新鲜缓存：零网络直接返回
  if (cached && Date.now() - cached.savedAt < ttlMs) {
    return cached.data;
  }

  try {
    const res = await fetch(url, {
      headers: cached?.etag ? { 'If-None-Match': cached.etag } : {},
    });

    // ② 304：内容没变，只续期，不重写数据
    if (res.status === 304 && cached) {
      await kv.set(key, { ...cached, savedAt: Date.now() });
      return cached.data;
    }

    if (!res.ok) throw new HttpError(res.status);

    const data = (await res.json()) as T;
    await kv.set(key, {
      data,
      etag: res.headers.get('etag'),
      savedAt: Date.now(),
    });
    return data;
  } catch (e) {
    // ③ 网络失败：有旧数据就先用旧数据（UI 负责标注"离线内容"）
    if (cached) return cached.data;
    throw e;
  }
}

6.2 只重试"值得重试"的错误 ​

ts
// src/net/withRetry.ts
import { HttpError } from '../sync/send';

/** 网络类错误（fetch 抛 TypeError）与 429/5xx 可重试；4xx 重试没有意义 */
function isRetryable(error: unknown): boolean {
  if (error instanceof TypeError) return true;
  if (error instanceof HttpError) return error.status === 429 || error.status >= 500;
  return false;
}

export async function withRetry<T>(
  task: () => Promise<T>,
  retries = 3,
): Promise<T> {
  let lastError: unknown;

  for (let attempt = 0; attempt <= retries; attempt += 1) {
    try {
      return await task();
    } catch (error) {
      lastError = error;
      if (!isRetryable(error) || attempt === retries) break;

      // 指数退避 + 抖动，避免断网恢复瞬间所有客户端同一秒重试
      const delay = Math.min(8_000, 500 * 2 ** attempt) * (0.5 + Math.random());
      await new Promise(resolve => setTimeout(resolve, Math.round(delay)));
    }
  }

  throw lastError;
}

  return {
    online,
    weak: online && (generation === '2g' || generation === '3g'),

// src/sync/lifecycle.ts
import { AppState } from 'react-native';
import NetInfo from '@react-native-community/netinfo';
import { drainOutbox } from './drain';
import { sendOutbox } from './send';

export function startSyncLifecycle(): () => void {
  // 回前台：用户可能刚打开 Wi-Fi，先尝试回放
  const appSub = AppState.addEventListener('change', next => {
    if (next === 'active') void drainOutbox(sendOutbox);
  });

  // 网络恢复：只在 online 变 true 的那一次触发
  let wasOnline = false;
  const netSub = NetInfo.addEventListener(state => {
    const online = state.isConnected === true && state.isInternetReachable !== false;
    if (online && !wasOnline) void drainOutbox(sendOutbox);
    wasOnline = online;
  });

  return () => {
    appSub.remove();
    netSub();
  };
}

十一、op-sqlite 的适用边界与最小查询 ​

op-sqlite 是本章主推的关系库，但不是"所有数据都往里塞"。轻量配置、单张小快照仍然走 KV；业务实体、队列、需要查询的数据才进 op-sqlite。满足下面任意两条，就该用关系库：

信号具体表现
多表关联笔记 ↔ 标签 ↔ 附件，需要 JOIN 或外键
复杂查询按多条件过滤、排序、分页、聚合，靠 JS 全量遍历已经卡
数据量阈值单表稳定超过几千行，或冷启动全量读进内存明显变慢
事务需求一次操作要写多张表，不能接受半成功
增量同步需要按 updated_at / 游标做增量拉取

最小查询示例（建表与迁移见 3.2）：

ts
// src/storage/notesRepo.ts
import { getDb, rowsOf } from './db';

export type NoteRow = {
  id: string;
  title: string;
  body: string;
  revision: number;
  dirty: number;
  updated_at: number;
};

export async function listNotes(limit = 50, offset = 0): Promise<NoteRow[]> {
  const result = await getDb().execute(
    `SELECT * FROM notes
     ORDER BY updated_at DESC
     LIMIT ? OFFSET ?`,
    [limit, offset],
  );
  return rowsOf<NoteRow>(result);
}

export async function countDirtyNotes(): Promise<number> {
  const result = await getDb().execute(
    'SELECT COUNT(*) AS total FROM notes WHERE dirty = 1',
  );
  return Number(result.rows[0]?.total ?? 0);
}

FAQ ​

Q1：所有数据都放 KV 不行吗？ 小数据可以。列表、队列、需要索引查询的数据不行：没有事务、没有索引、全量读写，数据量一大就卡，且并发写容易互相覆盖。

Q2：outbox 会不会重复提交？ 会，如果服务端不配合。客户端只能保证"同一幂等键只入队一次"，真正的去重必须在服务端落唯一索引/幂等表。网络超时但实际成功是最典型的重复来源。

Q3：MMKV 和 AsyncStorage 能混用吗？ 可以，但同一份数据只能有一个"主存储"。推荐 MMKV 放高频 KV、AsyncStorage 只留给 05 章已有的 persist，迁移完成后再删旧数据。

Q4：离线数据要加密吗？ 登录 token、个人信息、聊天记录建议加密（MMKV 支持 encryptionKey 加密存储；op-sqlite 默认构建是纯 SQLite，isSQLCipher() 返回 false，直接传 encryptionKey 会以 code 14 打开失败，必须先按 SQLCipher 目标自定义编译）。普通列表缓存可不加密，但要防止备份泄漏。

实测（iPhone 17 / iOS 26.5，op-sqlite 19.0.4）：open({ name: 'lab.db' }) 同步返回，耗时 1ms；PRAGMA journal_mode=WAL 返回 wal；事务内执行 PRAGMA user_version = 42 被接受（0 → 42，无报错）；1000 条单事务写入 14–25ms；10 万行建表 + 100×1000 批插 152–158ms、建索引 14–17ms、ADD COLUMN 0ms、分批回填 218–370ms（多次运行有波动）。加密库 open({ name: 'enc.db', encryptionKey: ... }) 在默认构建下失败：could not open database: unable to open database file (code 14)。

Q5：为什么不直接上 WatermelonDB / Realm？ 它们提供同步能力，但带来 schema、原生编译与迁移成本。团队小、实体少时，op-sqlite + outbox 更可控；等实体关系和冲突复杂度真的上来了再换。
