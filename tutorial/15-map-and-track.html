教程 15 · 地图与轨迹：画点建图、NMEA/RTK、抽稀与回放 ​

目标：把一串经纬度变成"可画、可存、可回放"的地图数据，并在两万点量级下仍然跟手。 版本锚点：React Native 0.87.1 + React 19.2.3 + TypeScript 严格模式；原型工程 mower-console-demo。 前置：14 · 通信底座。本章默认位姿已经从遥测链路进来。

割草机器人的地图和普通地图应用不一样：

  • 没有底图瓦片，只有一块自己画的边界；
  • 精度要求是"厘米级"，不是"大概在这条街";
  • 轨迹不是装饰，它决定了漏割、重割和电池消耗；
  • 手机性能有限，两万个点直接进 SVG path，低端机必卡。

所以本章的顺序是：先统一坐标，再建地块，再解析定位，最后才谈性能和回放。

一、坐标系统一：不要拿经纬度当 x/y ​

经纬度的"1 度"在东西和南北方向长度不同。直接 x = lon, y = lat 画出来，地块会横向拉伸，0.3m 的行距也没法算。

正确做法是以地块中心为原点，做一个局部切平面投影：

ts
// 原型：mower-console-demo/src/core/geo/projection.ts
const EARTH_RADIUS_M = 6_378_137;
const METERS_PER_DEG_LAT = (Math.PI / 180) * EARTH_RADIUS_M;

export class LocalProjection {
  private readonly metersPerDegLon: number;

  constructor(readonly origin: LatLon) {
    if (!Number.isFinite(origin.lat) || !Number.isFinite(origin.lon)) {
      throw new Error('投影原点必须是合法经纬度');
    }
    // 经度方向每度对应的米数随纬度收缩，必须按原点纬度算一次
    const cosLat = Math.cos((origin.lat * Math.PI) / 180);
    this.metersPerDegLon = METERS_PER_DEG_LAT * cosLat;
  }

  /** 经纬度 → 本地米制坐标（x 向东，y 向北） */
  toLocal(position: LatLon): Point {
    return {
      x: (position.lon - this.origin.lon) * this.metersPerDegLon,
      y: (position.lat - this.origin.lat) * METERS_PER_DEG_LAT,
    };
  }

  /** 本地米制坐标 → 经纬度，用于把规划路径回传给下位机 */
  toLatLon(point: Point): LatLon {
    return {
      lat: this.origin.lat + point.y / METERS_PER_DEG_LAT,
      lon: this.origin.lon + point.x / this.metersPerDegLon,
    };
  }
}

二、手动画点建图：先把"边界合法"定义清楚 ​

用户在地图上点几个点，围成一块地。看起来简单，实际要挡三类错误：

  1. 点数不足（少于 3 个点围不成面）；
  2. 自相交（"8"字形边界，面积算法会给出无意义结果）；
  3. 边界贴边/越界（割草机半径 0.35m，边界必须留 margin）。
ts
// 原型：mower-console-demo/src/core/geo/polygon.ts
export function polygonArea(points: ReadonlyArray<Point>): number {
  // 鞋带公式：有向面积取绝对值，不要求输入是顺时针还是逆时针
  let sum = 0;
  for (let i = 0; i < points.length; i += 1) {
    const a = points[i];
    const b = points[(i + 1) % points.length];
    sum += a.x * b.y - b.x * a.y;
  }
  return Math.abs(sum) / 2;
}

export function polygonSelfIntersects(points: ReadonlyArray<Point>): boolean {
  // 相邻边共享端点，跳过；非相邻边一旦相交就是非法地块
  for (let i = 0; i < points.length; i += 1) {
    const a1 = points[i];
    const a2 = points[(i + 1) % points.length];
    for (let j = i + 1; j < points.length; j += 1) {
      if (j === i || (j + 1) % points.length === i) continue;
      const b1 = points[j];
      const b2 = points[(j + 1) % points.length];
      if (segmentsIntersect(a1, a2, b1, b2)) return true;
    }
  }
  return false;
}

三、NMEA GGA / RMC：RTK 输出的"文本协议" ​

RTK 模块（如 u-blox ZED-F9P）最终吐给主控的，通常还是 NMEA 文本。它不神秘，就是逗号分隔 + XOR 校验：

text
$GNGGA,062735.00,3150.72345,N,11711.92345,E,4,24,0.6,32.1,M,-2.3,M,1.2,0000*5A
1
字段含义工程上怎么用
4fixQuality：0 无效 / 1 单点 / 2 差分 / 4 RTK 固定 / 5 RTK 浮点只有 4 才能用于高精度作业
24卫星数少于 10 时提示信号弱
0.6HDOP越大精度越差
1.2差分龄期（秒）超过 5s 时 RTK 解算基本不可信

3.1 校验和必须是 XOR，不是求和 ​

ts
// 原型：mower-console-demo/src/core/nmea/parser.ts
/** NMEA 校验和 = `$` 与 `*` 之间所有字符的 XOR */
export function computeNmeaChecksum(body: string): number {
  let checksum = 0;
  for (let i = 0; i < body.length; i += 1) {
    checksum ^= body.charCodeAt(i) & 0xff;
  }
  return checksum;
}

四、实时轨迹绘制与抽稀 ​

4.1 问题不在"点数多"，而在"每帧都重算" ​

两万个点直接拼成一个 SVG path，字符串可能有几百 KB。每次新点进来都重拼一次，主线程会被字符串拼接和路径解析吃掉。

原型的策略是双通道：

  • 实时通道：IncrementalDecimator 每来一个点做一次 O(1) 判断，只保留离上一个保留点超过 minSpacing 的点；
  • 收车通道：对整条轨迹做一次 RDP（Douglas-Peucker），保留拐弯特征。
ts
// 原型：mower-console-demo/src/core/geo/decimate.ts
export class IncrementalDecimator {
  private lastKept: TrackPoint | null = null;
  readonly kept: TrackPoint[] = [];

  constructor(private readonly minSpacingM = 0.08) {}

  push(point: TrackPoint): boolean {
    // 0.08m 对应 390pt 屏幕上约 1pt；比这更近的点画出来也是同一个像素
    if (!this.lastKept || distance(point, this.lastKept) >= this.minSpacingM) {
      this.kept.push(point);
      this.lastKept = point;
      return true;
    }
    return false;
  }

  /** 收尾时把最后一个原始点补上，保证轨迹终点不丢 */
  finish(lastRaw: TrackPoint | null): TrackPoint[] {
    if (lastRaw && this.lastKept !== lastRaw) {
      if (this.kept[this.kept.length - 1] !== lastRaw) this.kept.push(lastRaw);
    }
    return this.kept;
  }
}

最终渲染前再做一次 RDP：

ts
// 原型：mower-console-demo/src/core/geo/decimate.ts
export function decimateTrack(
  points: ReadonlyArray<TrackPoint>,
  options: DecimateOptions = {},
): DecimateResult {
  const started = nowMs();
  const minSpacing = options.minSpacingM ?? 0.08;
  const tolerance = options.toleranceM ?? 0.05;
  const radial = radialDecimate(points, minSpacing);   // 先做 O(n) 粗筛
  const reduced = douglasPeucker(radial, tolerance);  // 再做 O(n log n) 精筛
  return {
    points: reduced,
    rawCount: points.length,
    reducedCount: reduced.length,
    durationMs: nowMs() - started,                    // 把耗时带回 UI，便于真机评估
  };
}

4.2 实测数据与它的边界 ​

指标数值测量环境

输出点数约 200minSpacing=0.08m、tolerance=0.05m

这里要特别诚实："抽稀 109.8ms"不等于"一万点绘制流畅"。真正决定流畅度的是：

  1. path 字符串是否每帧重建；
  2. react-native-svg 的 path 解析是否在主线程；
  3. 是否每帧都在做坐标变换。

原型的优化是：抽稀后的点只在"点数变化超过阈值"或"用户停止拖动"时重建 path，平移/缩放只改 transform，不重建数据。这个策略在 iOS 模拟器上主观跟手，但没有跑过 Instruments，也没有低端 Android 真机数据。

4.3 一笔画 path 的生成 ​

ts
// 原型：mower-console-demo/src/ui/MapCanvas.tsx（节选）
function toPath(points: ReadonlyArray<Point>): string {
  if (points.length === 0) return '';
  // 只生成一次 M + L 指令；不要在渲染函数里对每个点做字符串模板拼接
  const [first, ...rest] = points;
  let d = `M${first.x.toFixed(2)} ${first.y.toFixed(2)}`;
  for (const p of rest) d += `L${p.x.toFixed(2)} ${p.y.toFixed(2)}`;
  return d;
}

五、轨迹回放：按时间轴推进，不按数组下标 ​

"回放"最常见的错误实现是：index++，每个 tick 取下一个点。它有两个问题：

  1. 丢包造成的长间隔会让机器人"瞬移"；
  2. 用户变速时，运动速度不均匀。

正确做法是每个样本自带时间戳 t，回放位置由"当前时间"决定：

ts
// 原型：mower-console-demo/src/core/replay/player.ts
step(dtMs: number): ReplayFrame {
  if (this.playing) {
    // dt 是真实经过时间，乘以倍速；UI 帧率变化不会改变回放速度
    this.elapsedMs = Math.min(this.durationMs, this.elapsedMs + dtMs * this.speed);
    if (this.elapsedMs >= this.durationMs) this.playing = false;
  }
  return this.frameAt(this.elapsedMs);
}

frameAt(offsetMs: number): ReplayFrame {
  const target = this.startTime + Math.max(0, Math.min(this.durationMs, offsetMs));
  const index = findSegment(this.samples, target); // 二分查找所在区间
  const a = this.samples[index];
  const b = this.samples[Math.min(index + 1, this.samples.length - 1)];
  const span = b.t - a.t;
  const fraction = span > 0 ? Math.max(0, Math.min(1, (target - a.t) / span)) : 0;

  return {
    position: {
      x: a.x + (b.x - a.x) * fraction, // 线性插值，位置连续
      y: a.y + (b.y - a.y) * fraction,
    },
    index,
    progress: this.durationMs > 0 ? (target - this.startTime) / this.durationMs : 1,
    fraction,
    headingDeg: (Math.atan2(b.x - a.x, b.y - a.y) * 180) / Math.PI,
    timestamp: target,
    finished: offsetMs >= this.durationMs,
  };
}

回放时还要区分两种轨迹：

  • 原始轨迹：用于统计、导出、复盘，不能抽稀；
  • 显示轨迹：抽稀后用于绘制，可以随缩放级别变化。

UI 上建议把"已走轨迹"画成实线，"回放游标"单独画一个点，不要让游标去修改轨迹数组。

六、关键点 ​

  1. 先投影再计算。经纬度只用于传输和存储，几何计算一律在本地米制坐标里做。
  2. 地块合法性前置校验：点数、自相交、margin、障碍物是否越界。
  3. NMEA 先校验后解析，GGA 的日期要从 RMC 补。
  4. 抽稀分两档：实时 O(1) 径向过滤，收车 RDP。
  5. 抽稀只服务绘制，统计、导出、回放必须用原始点。
  6. 回放按时间轴插值，不按数组下标推进。
  7. 性能结论要带测量环境，模拟器数字不能直接外推到低端 Android。

七、常见坑 ​

  1. 直接拿经纬度当 x/y：地块横向拉伸，0.3m 行距算成 0.4m，规划直接错。
  2. 忘记经度随纬度收缩：在纬度 40° 的地方，经度方向每度只有约 85km，不是 111km。
  3. 抽稀后拿去算面积/周长：RDP 会砍掉小拐弯，面积偏小，覆盖率统计跟着错。
  4. 增量抽稀不补终点：最后一个点如果离上一个保留点太近会被丢掉，轨迹"断尾"。
  5. 每帧重建 path：点数一多就掉帧，且 toFixed 字符串拼接在主线程。
  6. 回放按 index 推进：丢包 3 秒后机器人瞬移，用户以为定位坏了。
  7. GGA 单独解析：没有日期，时间戳全是 null 或 1970 年。
  8. 自相交多边形不做校验：鞋带公式仍会返回一个数，但那个数没有几何意义。

八、验收清单 ​

  • [ ] 地块 > 3 点、无自相交、边界留出机器半径；
  • [ ] 面积/周长用本地米制坐标计算，并有单元测试；
  • [ ] NMEA 校验和错误会抛错，不会被静默吞掉；
  • [ ] GGA 的时间戳能通过 RMC 补齐；
  • [ ] 实时轨迹使用增量抽稀，终点不丢；
  • [ ] 绘制 path 不在每帧重建；
  • [ ] 回放支持播放/暂停/倍速/拖动，位置连续；
  • [ ] 抽稀只用于显示，统计与导出使用原始轨迹；
  • [ ] 性能数字标注了设备和测量项（抽稀耗时 ≠ FPS）。
