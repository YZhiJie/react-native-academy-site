教程 11 · 离线可靠性：毒消息、背压与崩溃恢复 ​

目标：把 09 章 的 outbox 从"能跑"推到"坏了也能自愈"。 版本锚点：React Native 0.87.1（bridgeless + Hermes）；@op-engineering/op-sqlite@19.0.4、react-native-blob-util@0.25.1。 前置：09 · 离线能力——本章的 outbox 表、drainOutbox、幂等键都来自那里。

09 章的 outbox 已经具备三个基本动作：入队、claim、失败退避。但它默认了三件过于乐观的事：

  1. 失败都会自愈——实际上 400/404 这类错误重试一万次也不会成功；
  2. 队列不会无限长——实际上离线一周、用户狂点，队列能撑爆磁盘；
  3. 进程不会在中间死——实际上系统随时可能杀 App。

本章逐条补上。先给结论：可靠性不是"多写几个 catch"，而是把状态机、配额和故障注入都变成可验收的约束。

一、毒消息：先能识别，再谈重试 ​

1.1 什么叫毒消息 ​

同一条 outbox 记录满足任意两条，就应判定为毒消息：

判定信号说明
同类错误连续出现同一 idempotency_key 连续失败 ≥ 3 次，且错误码不变
错误不可重试400 / 403 / 404 / 409 / 422 等 4xx（408、429 除外）
重试次数达上限attempts >= 5
数据本身有问题payload 无法反序列化、必填字段缺失、超出服务端长度限制
ts
// src/sync/errorClass.ts
import { HttpError } from './send';

export type ErrorClass = 'transient' | 'permanent' | 'auth';

/** 只把"再试可能成功"的错误留在队列里，其余尽快进死信 */
export function classifyError(error: unknown): ErrorClass {
  if (error instanceof HttpError) {
    if (error.status === 401 || error.status === 403) return 'auth';
    if (error.status === 408 || error.status === 429 || error.status >= 500) {
      return 'transient';
    }
    // 400/404/409/422：请求或数据有问题，重试不会变好
    return 'permanent';
  }

  // fetch 在网络层抛 TypeError（断网、DNS、连接重置）
  if (error instanceof TypeError) return 'transient';

  // 未知错误先按可重试处理，但必须记录并观察，不能静默吞掉
  return 'transient';
}

1.2 死信表：与 outbox 同库、同事务 ​

ts
// src/sync/dlq.ts
import { getDb, rowsOf, type OutboxRow } from '../storage/db';

export type DeadRow = OutboxRow & {
  attempts: number;
  last_error: string;
  moved_at: number;
};

/** 09 章 schema 是 v1；本章追加 v2：死信表 + 索引 */
export async function migrateV2(): Promise<void> {
  const db = getDb();
  const version = await db.execute('PRAGMA user_version;');
  if (Number(version.rows[0]?.user_version ?? 0) >= 2) return;

  await db.transaction(async tx => {
    await tx.execute(`
      CREATE TABLE IF NOT EXISTS outbox_dead (
        id              TEXT PRIMARY KEY NOT NULL,
        entity          TEXT NOT NULL,
        op              TEXT NOT NULL,
        payload         TEXT NOT NULL,
        idempotency_key TEXT NOT NULL,
        attempts        INTEGER NOT NULL,
        last_error      TEXT NOT NULL,
        moved_at        INTEGER NOT NULL
      );
    `);
    await tx.execute(`
      CREATE INDEX IF NOT EXISTS idx_outbox_dead_key
      ON outbox_dead (idempotency_key);
    `);
    await tx.execute('PRAGMA user_version = 2;');
  });
}

/** 把一条记录从 outbox 移到死信：两步必须同事务，否则会丢消息 */
export async function quarantine(row: OutboxRow, reason: string): Promise<void> {
  const db = getDb();
  const now = Date.now();

  await db.transaction(async tx => {
    await tx.execute(
      `INSERT OR REPLACE INTO outbox_dead
         (id, entity, op, payload, idempotency_key, attempts, last_error, moved_at)
       VALUES (?, ?, ?, ?, ?, ?, ?, ?)`,
      [
        row.id,
        row.entity,
        row.op,
        row.payload,
        row.idempotency_key,
        row.attempts,
        reason.slice(0, 500),
        now,
      ],
    );
    await tx.execute('DELETE FROM outbox WHERE id = ?', [row.id]);
  });
}

1.3 重入：只能人工或受控自动 ​

ts
// src/sync/replayDead.ts
import { getDb, rowsOf } from '../storage/db';
import type { DeadRow } from './dlq';

export async function replayDead(id: string): Promise<boolean> {
  const db = getDb();
  const found = await db.execute('SELECT * FROM outbox_dead WHERE id = ?', [id]);
  const dead = rowsOf<DeadRow>(found)[0];
  if (!dead) return false;

  await db.transaction(async tx => {
    // 幂等键仍在 outbox 里时 INSERT 会触发 UNIQUE 冲突 → 整个事务回滚，
    // 这正是我们想要的：不能因为"重入"制造第二条重复指令
    await tx.execute(
      `INSERT INTO outbox
         (id, entity, op, payload, idempotency_key, status, attempts,
          next_attempt_at, locked_at, created_at)
       VALUES (?, ?, ?, ?, ?, 'pending', 0, 0, 0, ?)`,
      [
        dead.id,
        dead.entity,
        dead.op,
        dead.payload,
        dead.idempotency_key,
        Date.now(),
      ],
    );
    await tx.execute('DELETE FROM outbox_dead WHERE id = ?', [id]);
  });

  return true;
}

重入策略：

场景做法
数据修复后后台运营工具按 id/幂等键重入，必须记录操作人
服务端已修复发布后自动重入最近 24 小时的死信，限速 1 条/秒
401/403不要自动重入，先刷新登录态，再人工确认
payload 结构错误只能丢弃 + 上报，重入没有意义

常见坑：把 failed 状态留在 outbox 里当死信。结果是回放扫描永远要过滤它，表越长越慢，而且无法区分"暂时失败"和"永久失败"。死信必须独立表。

二、背压：队列上限、实体保序与磁盘配额 ​

2.1 队列上限：软上限 + 硬上限 ​

ts
// src/sync/backpressure.ts
import ReactNativeBlobUtil from 'react-native-blob-util';
import { getDb } from '../storage/db';

export class QueueFullError extends Error {
  constructor(readonly pending: number) {
    super(`offline queue full: ${pending}`);
  }
}

const SOFT_LIMIT = 5_000;   // 超过后停止接收新的非关键写
const HARD_LIMIT = 8_000;   // 超过后连关键写也拒绝，提示用户联网
const MIN_FREE_BYTES = 50 * 1024 * 1024;

export async function queueDepth(): Promise<number> {
  const result = await getDb().execute(
    `SELECT COUNT(*) AS total FROM outbox WHERE status IN ('pending', 'syncing')`,
  );
  return Number(result.rows[0]?.total ?? 0);
}

export async function assertQueueCapacity(critical: boolean): Promise<void> {
  const depth = await queueDepth();
  const limit = critical ? HARD_LIMIT : SOFT_LIMIT;
  if (depth >= limit) throw new QueueFullError(depth);
}

/** 磁盘余量：iOS 用 free，Android 用 internal_free；字段不可用时不要误判 */
export async function hasDiskRoom(): Promise<boolean> {
  const df = await ReactNativeBlobUtil.fs.df();
  const free = df.free ?? Number(df.internal_free ?? 0);
  if (!Number.isFinite(free) || free <= 0) return true;
  return free > MIN_FREE_BYTES;
}

queueDepth + insert 不是原子的，所以这是"软上限"；真要做到硬上限，把 count 和 insert 放进同一个 db.transaction。代价是每次写都多一次全表 count——用状态索引后可以接受。

2.2 按实体保序：同一实体同时只允许一条在飞 ​

09 章的 drainOutbox 用 ORDER BY created_at 全局排队。多实体场景下这会互相拖累：一个卡住的笔记不该堵住所有设置同步。改成"同实体串行、跨实体并行"：

sql
SELECT o.*
FROM outbox o
WHERE o.status = 'pending'
  AND o.next_attempt_at <= ?
  AND NOT EXISTS (
    SELECT 1 FROM outbox s
    WHERE s.entity = o.entity AND s.status = 'syncing'
  )
ORDER BY o.created_at ASC
LIMIT ?;

2.3 批量大小与磁盘写满 ​

参数建议理由
单批回放20 条失败影响面小，退避粒度细
单批事务写入100~500 条太大占锁久，太小写放大
单条 payload< 100KB再大走文件，DB 只存路径
磁盘保留≥ 50MB低于阈值停止入队，避免 SQLite 写失败损坏

磁盘满时的降级顺序：

  1. 停止接收非关键写（埋点、预取、非首屏缓存）；
  2. 清理可再生的缓存（图片、旧离线包），不要碰 outbox；
  3. 仍不足 → 拒绝新写并提示"存储空间不足，请清理后再试"；
  4. 绝不自动删除 outbox 里的业务变更，那是用户没同步的数据。

三、崩溃恢复：每个阶段被杀，语义要可预期 ​

3.1 四个崩溃点 ​

崩溃点数据库状态恢复后行为
入队事务中事务未提交，notes/outbox 都不存在用户重试即可，无半成功
入队事务后、回放前outbox = pending正常回放
claim 后、发送前outbox = syncing，locked_at 有值超过 2 分钟回到 pending
服务端成功、本地删除前outbox = syncing，服务端已有记录重新发送，靠服务端幂等键去重

前三个靠本地状态机，第四个只能靠服务端唯一索引。客户端无法知道"超时的那次请求到底成没成功"。

3.2 恢复代码 ​

ts
// src/sync/recovery.ts
import { getDb } from '../storage/db';

/**
 * 冷启动时先跑：把僵死的 syncing 放回 pending。
 * 只按时间判断，不按进程 id——进程重启后旧 pid 没有意义。
 */
export async function recoverStaleClaims(staleMs = 120_000): Promise<number> {
  const result = await getDb().execute(
    `UPDATE outbox
     SET status = 'pending', locked_at = 0
     WHERE status = 'syncing' AND locked_at < ?`,
    [Date.now() - staleMs],
  );
  return result.rowsAffected;
}

/** 启动顺序：迁移 → 恢复僵死 claim → 再允许回放 */
export async function bootOfflineLayer(initDb: () => Promise<void>): Promise<void> {
  await initDb();
  await recoverStaleClaims();
}

3.3 不丢、不重、不卡死的三条约束 ​

约束靠什么保证不能靠什么
不丢入队事务 + 死信表"发送失败就重试"（进程可能已经死了）
不重服务端 idempotency_key 唯一索引客户端内存里的 Set
不卡死claim 超时回收 + 最大重试次数无限退避（会让队列永久堵住）

实测（2026-11，iPhone 17 / iOS 26.5 模拟器，op-sqlite 19.0.4）：80 条 outbox 消息，先用 simctl terminate 在 claim 后/发送中/落盘前连续强杀 3 次，再冷启动跑完。结果：启动时回收 2 条僵死 claim，服务端共收到 82 次请求、去重后 80 个 id（2 次重复由幂等键吸收），本地 attempts 合计 82、收据 80 条、最终 byState 只剩 sent，无 pending/卡死。实验用 5s 回收阈值，生产建议按弱网上传时长再调大。

常见坑：用 attempts 同时做"退避次数"和"死信阈值"。一旦人工重入，attempts 归零，反而不该死信；建议把 attempts 与 last_error 一起进死信表，重入后重新计数。

四、故障注入矩阵 ​

故障注入方式预期行为验收
断网飞行模式 / adb shell svc wifi disable入队成功，回放走退避，UI 显示离线outbox 不减少，服务端 0 请求
弱网Network Link Conditioner 3G / 30% 丢包请求有超时，退避带抖动，不并发轰炸重试间隔递增，无雪崩
超时服务端 sleep > 客户端 timeout记为 transient，进入退避不误判为永久失败
500服务端固定返回 5005 次后进死信，告警outbox_dead 有记录，outbox 清空
部分成功服务端先落库再断开连接客户端重发，服务端去重服务端审计接口 duplicates = 0
进程被杀claim 后 adb shell am force-stop冷启动 2 分钟后回收最终 pending 数下降，不永久卡 syncing
磁盘满填充沙盒至剩余 < 50MB停止非关键入队，不删 outbox队列深度不再增长，业务数据仍在
时钟跳变手动改系统时间 ±2h版本号策略不受影响；LWW 只用 updatedAt 兜底合并结果不因时间跳变而回退

五、可执行验收：模拟注入 + 服务端核对 ​

5.1 客户端：不变量检查 ​

ts
// src/sync/__checks__/invariants.ts
import { getDb } from '../../storage/db';

export async function assertOutboxInvariants(): Promise<void> {
  const db = getDb();

  // ① 同一幂等键不能在 outbox 里出现两次
  const dup = await db.execute(`
    SELECT idempotency_key, COUNT(*) AS total
    FROM outbox
    GROUP BY idempotency_key
    HAVING total > 1
  `);
  if (dup.rows.length > 0) throw new Error('duplicate idempotency key in outbox');

  // ② 不允许长期卡在 syncing
  const stuck = await db.execute(`
    SELECT COUNT(*) AS total
    FROM outbox
    WHERE status = 'syncing' AND locked_at < ?
  `, [Date.now() - 120_000]);
  if (Number(stuck.rows[0]?.total ?? 0) > 0) throw new Error('stale syncing rows');

  // ③ 死信不能悄悄堆着不告警
  const dead = await db.execute('SELECT COUNT(*) AS total FROM outbox_dead');
  const deadCount = Number(dead.rows[0]?.total ?? 0);
  if (deadCount > 0) {
    // 真实项目：上报指标并触发告警，而不是 throw 让 App 崩
    console.warn(`[offline] dead letters: ${deadCount}`);
  }
}

5.2 演练脚本：同一份数据跑 10 次故障 ​

ts
// src/sync/__checks__/drill.ts
import { getDb } from '../../storage/db';
import type { OutboxRow } from '../../storage/db';
import { enqueueNote } from '../outbox';
import { drainOutbox } from '../drain';
import { HttpError } from '../send';
import { assertOutboxInvariants } from './invariants';

export type Fault = 'offline' | 'timeout' | 'http500' | 'http409' | 'kill-after-send';

/**
 * 注意：这里只能模拟"进程内抛错"。
 * 真正的 OS 杀进程必须用 debug 构建的 crash hook 或 adb force-stop，
 * 进程内 try/catch 覆盖不了。
 */
export async function runFaultDrill(fault: Fault): Promise<void> {
  const db = getDb();
  await db.execute('DELETE FROM outbox');
  await db.execute('DELETE FROM outbox_dead');

  for (let i = 0; i < 10; i += 1) {
    await enqueueNote({
      noteId: `drill-${i}`,
      title: 'drill',
      body: 'x',
      revision: 1,
    });
  }

  let serverCommits = 0;

  await drainOutbox(async (row: OutboxRow) => {
    if (fault === 'offline') throw new TypeError('Network request failed');
    if (fault === 'timeout') throw new TypeError('timeout');
    if (fault === 'http500') throw new HttpError(500);
    if (fault === 'http409') throw new HttpError(409);

    serverCommits += 1;
    if (fault === 'kill-after-send' && serverCommits === 1) {
      throw new Error('simulated crash after server commit');
    }
  });

  await assertOutboxInvariants();
  console.log(`[drill] ${fault}: serverCommits=${serverCommits}`);
}

  const res = await fetch(`${baseUrl}/__audit/duplicates`);

验收顺序：

  1. 客户端依次跑 offline → timeout → 500 → 409 → kill-after-send；
  2. 每次跑完 assertOutboxInvariants()；
  3. 恢复网络后回放清空；
  4. 调服务端审计接口，确认重复数为 0；
  5. 才能把这一版标记为"可靠性回归通过"。

六、常见坑 ​

  1. 把 409 当临时失败：版本冲突是业务冲突，继续重试只会无限循环，应该转人工/合并。
  2. 死信和 outbox 混在一起：扫描变慢、无法告警、人工重入误操作。
  3. 队列没有上限：离线一周后 SQLite 膨胀，用户升级前先卡死。
  4. 用进程内变量防重：let sending = true 只防同进程并发，防不了崩溃后重发。
  5. 磁盘满时清理 outbox：这是用户没同步的数据，删了就真丢了。
  6. claim 超时设得太短：弱网下大 payload 还没传完就被回收，导致重复发送放大。

七、验收清单 ​

  • [ ] 4xx（非 408/429）不会无限重试；
  • [ ] 死信有独立表、有告警、有受控重入；
  • [ ] 队列有软/硬上限，磁盘低于阈值停止非关键写；
  • [ ] 同一实体不会并发回放；
  • [ ] 冷启动会回收僵死 syncing；
  • [ ] 入队与"移到死信"都是事务；
  • [ ] 服务端有幂等唯一索引与审计接口；
  • [ ] 八类故障至少各跑一次，且保留结果。

八、能讲清的，和必须真实工程练的 ​

本章能讲清的：毒消息判定、死信表结构、背压阈值、claim 恢复、故障矩阵、可执行验收顺序。这些是设计原则和代码骨架。

必须真实工程练的：

  • 真实 Android 厂商的杀进程时机与后台限制；
  • 弱网下的真实超时分布（不是模拟器能复现的）；
  • 服务端幂等索引的真实实现与审计能力；
  • 千万级用户下 outbox 深度分布与磁盘压力。
