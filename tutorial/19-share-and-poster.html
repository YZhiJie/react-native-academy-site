教程 19 · 分享传播：微信 JS-SDK、海报生成与回流归因 ​

目标：把"分享"拆成三段可控的链路——卡片配置、海报生成、回流归因；并明确哪些能力必须在真实公众号环境才能验证。 版本锚点：React 19.2.3 + TypeScript 5.9 严格模式；微信 JS-SDK 部分只做封装与降级，未在真实公众号验证。 前置：17 · 工程骨架、18 · 抽奖与风控。 原型：activity-h5-demo（仓库外独立工程）。

活动页的流量结构通常是"一小撮种子用户 + 大量被动回流"。种子用户从哪里来？分享。

而分享链路上有三个断点，每一个都会让传播系数断崖式下跌：

  1. 分享卡片不对：标题是默认的网页标题，缩略图是空白，点开率极低；
  2. 海报生成失败：用户想发朋友圈，点了没反应，或者图糊了、被裁了；
  3. 回来了但算不到人头：邀请人拿不到助力，活动方也说不清哪个渠道有效。

这一章逐个解决，并守住一条底线：没有在真实微信里验证过的能力，只能写"实现了封装与降级"，不能写"已验证可用"。

三段的技术难度依次递减，但失败率依次递增。卡片分享依赖公众号配置，最容易卡在"签名对不上"；海报依赖 Canvas 与设备能力，最容易卡在"图糊了 / 保存失败"；归因依赖参数设计，最容易卡在"参数被吞掉"。

二、微信 JS-SDK：先接受它的约束 ​

2.1 四道前置条件 ​

条件说明不满足的后果
已认证公众号订阅号 / 服务号需完成微信认证无法获取 jsapi_ticket
JS 安全域名在公众号后台配置，且必须 HTTPSconfig 直接报 invalid signature
后端签名用 jsapi_ticket 对 noncestr + timestamp + url 做 SHA-1签名错误
URL 精确匹配签名用的 URL 必须与当前页面 URL 去掉 hash 后完全一致带参进入时必错

最后一条是最高频的坑：活动链接通常带 ?inviter=xxx&channel=qr，如果后端签名时用了"干净"的 URL，前端在带参页面里 config 一定失败。

2.2 封装：把"失败"当成正常分支 ​

ts
// 原型：activity-h5-demo/src/core/share.ts（节选）
export async function setupWechatShare(
  sdk: WechatJsSdk | null,
  signature: ShareSignature | null,
  payload: WechatSharePayload,
  userAgent: string,
): Promise<ShareSetupResult> {
  if (!isWechatUserAgent(userAgent)) {
    return { mode: 'copy_link', reason: 'not_wechat' };
  }
  if (!sdk) {
    return { mode: 'copy_link', reason: 'sdk_missing' };
  }
  if (!signature) {
    return { mode: 'copy_link', reason: 'config_failed' };
  }

  const ready = new Promise<boolean>(resolve => {
    // 微信两个回调都只触发一次，用 once 语义避免重复 resolve
    sdk.ready(() => resolve(true));
    sdk.error(() => resolve(false));
    sdk.config({
      debug: false,
      appId: signature.appId,
      timestamp: signature.timestamp,
      nonceStr: signature.nonceStr,
      signature: signature.signature,
      jsApiList: ['updateAppMessageShareData', 'updateTimelineShareData'],
    });
  });

  const configured = await ready;
  if (!configured) {
    return { mode: 'copy_link', reason: 'config_failed' };
  }
  if (!sdk.updateAppMessageShareData) {
    return { mode: 'copy_link', reason: 'api_missing' };
  }

  sdk.updateAppMessageShareData(payload);
  sdk.updateTimelineShareData?.({ title: payload.title, link: payload.link, imgUrl: payload.imgUrl });
  return { mode: 'jssdk' };
}

四个降级原因各有不同处理方式：

reason含义UI 该做什么
not_wechat不在微信内显示"复制链接"或系统分享
sdk_missingSDK 脚本没加载成功（弱网常见）重试加载或直接降级

不要 throw。分享失败不该阻塞抽奖主流程，用户抽完奖看到报错弹窗，体验比"没分享成功"更糟。

2.3 三条必须知道的限制 ​

  1. 朋友圈不能由 JS 直接触发。只能引导用户点右上角菜单，所以文案要写"点击右上角 ··· 分享到朋友圈"，而不是做一个假的"分享到朋友圈"按钮。
  2. iOS 与 Android 的分享卡片表现不同。同一份 title/desc/imgUrl，两端展示的字段数量不一样，缩略图比例要求也不同（常用 5:4）。这部分必须在真机验证，本章未验证。
  3. 老接口已废弃。onMenuShareTimeline 等在微信 6.7.2 之后被 updateTimelineShareData 替代，新项目不要再接老接口。

2.4 分享链接：参数放 query，不要放 hash ​

ts
// 原型：activity-h5-demo/src/core/share.ts
export function buildShareLink(origin: string, params: { aid: string; inviter: string; channel: string }): string {
  const url = new URL('/activity', origin);
  url.searchParams.set('aid', params.aid);
  url.searchParams.set('inviter', params.inviter);
  url.searchParams.set('channel', params.channel);
  // 分享链接必须带自己的标记，否则无法把它和自然流量区分开
  url.searchParams.set('from', 'share');
  return url.toString();
}

原因很实际：很多 H5 用 hash 路由（/#/draw），而微信在部分场景下会丢弃 hash 之后的内容，或者签名时要求排除 hash。把归因参数放在 query 里，两端行为一致。

channel 字段是复盘的基础：二维码、分享卡片、朋友圈、外部投放，每个来源一个值，后面才能做渠道对比（第 20 章）。

三、回流归因：first-touch + 归因窗口 ​

3.1 参数解析：兼容二维码 scene ​

微信带参二维码只会带回一个 scene 字符串，不会展开成多个参数。所以要在 scene 里再塞一组 k=v：

ts
// 原型：activity-h5-demo/src/core/attribution.ts
export function parseLaunchParams(search: string): LaunchParams {
  const query = new URLSearchParams(search.startsWith('?') ? search.slice(1) : search);
  const scene = query.get('scene');

  // 微信带参二维码只会带回一个 scene，约定 scene 内部再放一组 k=v
  const sceneQuery = scene ? new URLSearchParams(scene.includes('=') ? scene : `i=${scene}`) : null;

  return {
    activityId: query.get('aid') ?? sceneQuery?.get('aid') ?? null,
    inviterId: query.get('inviter') ?? sceneQuery?.get('inviter') ?? sceneQuery?.get('i') ?? null,
    channel: query.get('channel') ?? sceneQuery?.get('channel') ?? null,
    scene,
  };
}

3.2 绑定策略：固定规则，别让关系"跳来跳去" ​

ts
// 原型：activity-h5-demo/src/core/attribution.ts（节选）
export function decideBinding(userId, existing, params, options): BindDecision {
  const inviterId = params.inviterId;
  if (!inviterId) {
    return { binding: existing, action: 'reject_missing', reason: '启动参数里没有邀请人' };
  }
  if (inviterId === userId) {
    return { binding: existing, action: 'reject_self', reason: '不能绑定自己' };
  }
  if (existing) {
    const ageDays = (options.now - existing.boundAt) / 86_400_000;
    if (existing.inviterId === inviterId) {
      return { binding: existing, action: 'keep', reason: '同一邀请人，无需重复绑定' };
    }
    if (ageDays <= options.windowDays) {
      // first-touch：窗口内不允许改绑，防止"分享到多个群互相抢量"
      return { binding: existing, action: 'keep', reason: `已绑定且在 ${options.windowDays} 天归因窗口内` };
    }
  }

  return {
    binding: { inviterId, boundAt: options.now, channel: params.channel, source: options.source },
    action: 'bind',
    reason: existing ? '原绑定已超出归因窗口' : '首次绑定',
  };
}

四种结果的业务含义：

action场景数据处理
bind首次进入或被邀请人换了写入邀请关系，记录 source 与 channel
keep已绑定且窗口内不覆盖，但回流事件仍要上报（用于算活跃）
reject_self自己点自己的链接拒绝，并计入风控指标
reject_missing自然流量不绑定，计入"自然量"渠道

为什么用 first-touch：如果允许 last-touch 覆盖，A 把链接发到 10 个群，B 只要在活动期间再点一次别人的链接，A 的功劳就被抹掉了。反过来，如果永远不覆盖，用户换了设备或半年后重新被邀请，关系又绑不上——所以要有归因窗口，原型的默认值是 7 天，具体数值是业务决定。

3.3 归因不等于发奖 ​

绑定关系只回答"谁邀请的"，发奖还要再走一层助力计数（第 18 章）。两者必须分离：

  • 绑定：一次写入，长期有效，按归因窗口更新；
  • 助力：按"助力记录"幂等，有上限、有去重、不能自助力。

把这两件事混在一张表里，会出现"改绑一次就多一份奖励"的漏洞。

四、海报：布局是纯函数，绘制是薄层 ​

4.1 为什么先做布局 ​

海报出问题，90% 不是绘制 API 用错，而是布局算错：文字压到二维码、超长昵称把头像挤出去、安全区没算导致底部被裁。

把布局提成纯函数后，这些问题都能在 Node 里断言：

ts
// 原型：activity-h5-demo/src/features/poster/layout.ts（节选）
export function computePosterLayout(input: PosterInput): PosterLayout {
  const { designWidth: w, designHeight: h } = input;
  const padding = Math.round(w * 0.08);
  const avatarSize = Math.round(w * 0.14);
  const footerHeight = Math.round(h * 0.06);

  // 二维码固定在安全区上方；safeBottom 由调用方从 env(safe-area-inset-bottom) 换算
  const qrRect: Rect = {
    x: Math.round((w - qr) / 2),
    y: h - footerHeight - input.safeBottom - qr - Math.round(h * 0.05),
    width: qr,
    height: qr,
  };

  const prizeTop = Math.round(h * 0.46);
  const prizeHeight = Math.round(h * 0.16);
  // 正文区与二维码之间至少留 24 设计像素；不够就判定溢出，由绘制层缩字号
  const overflow = prizeTop + prizeHeight + 24 > qrRect.y;

  return { width: w, height: h, background: { ... }, avatar: { ... }, nickname: { ... }, prizeText: { ... }, qr: qrRect, footer, lines, overflow };
}

4.2 折行：按视觉宽度，不按字符数 ​

ts
// 原型：activity-h5-demo/src/features/poster/layout.ts
export function wrapText(text: string, maxUnitsPerLine: number, maxLines: number): string[] {
  const lines: string[] = [];
  let current = '';
  let units = 0;

  for (const char of text) {
    const width = /[\u4e00-\u9fa5]/.test(char) ? 1 : 0.55;
    if (units + width > maxUnitsPerLine && current.length > 0) {
      lines.push(current);
      current = '';
      units = 0;
      if (lines.length === maxLines) break;
    }
    current += char;
    units += width;
  }
  // ...
}

中文一个字宽、英文与数字按 0.55 字宽估算。这不是精确排版（真正精确要 measureText），但对海报文案足够——奖品名通常是中文短句。如果活动允许用户自定义文案，就必须改成 measureText 逐个测量。

4.3 绘制：顺序就是图层顺序 ​

ts
// 原型：activity-h5-demo/src/features/poster/draw.ts（节选）
/**
 * 绘制顺序 = 图层顺序：背景 → 头像 → 昵称 → 奖品文案 → 二维码。
 * 二维码最后画，保证它永远不会被文案或装饰盖住；文案溢出时先缩字号再画。
 */
export function drawPoster(ctx: CanvasLike, layout: PosterLayout, assets: PosterAssets): DrawCall[] {
  ctx.save();
  ctx.fillStyle = '#1b1030';
  ctx.fillRect(layout.background.x, layout.background.y, layout.background.width, layout.background.height);

  if (assets.avatar) drawImage(ctx, calls, assets.avatar, layout.avatar);

  // 溢出时按行数缩字号，而不是截断内容：奖品名被截断会引发客诉
  const prizeFontSize = layout.overflow
    ? Math.round(layout.prizeText.height * 0.28)
    : Math.round(layout.prizeText.height * 0.34);
  // ...
  drawImage(ctx, calls, assets.qr, layout.qr);
  ctx.restore();
  return calls;
}

export function toCanvasTransform(cssWidth: number, designWidth: number, dpr: number) {
  const scale = cssWidth / designWidth;
  return {
    cssWidth,
    dpr,
    scale,
    pixelWidth: Math.round(cssWidth * dpr),
    toPixel: (value: number) => Math.round(value * scale * dpr),

五、关键点 ​

  1. 分享是增强功能，不是主流程。任何分享失败都必须降级，不能抛错阻塞抽奖。
  2. JS-SDK 有四个前置条件：认证公众号、JS 安全域名、后端签名、URL 精确匹配。
  3. 签名 URL 必须与当前页面（去 hash）一致，带参分享链接是最常见的翻车点。
  4. 朋友圈不能由 JS 触发，只能引导用户点右上角。
  5. 分享参数放 query，不要放 hash。
  6. 归因参数要兼容 scene 的两种编码（整体 k=v 编码 / 直接放邀请码）。
  7. 绑定用 first-touch + 归因窗口，绑定与助力是两层，不要合并。
  8. 海报布局是纯函数，能在 Node 里断言溢出、越界、二维码位置。
  9. 中文折行按视觉宽度，超出用省略号；用户可自定义文案时才升级到 measureText。
  10. 绘制顺序决定图层，二维码最后画。
  11. DPR 影响清晰度也影响内存，长边建议不超过 2000px。
  12. Object URL 用完必须 revoke。

六、常见坑 ​

  1. 用页面默认标题分享：卡片标题是"加载中…"，点开率接近 0。
  2. 签名 URL 带了完整 hash：微信要求去掉 hash，不处理就 invalid signature。
  3. config 失败后 throw：抽奖主流程被一个可选能力打断。
  4. 签名失败当用户错误提示：用户什么也没做错，应该静默降级 + 上报。
  5. 分享到朋友圈做成按钮：微信不允许 JS 触发，按钮点了没反应。
  6. 邀请参数放 hash：部分场景被微信丢弃，归因丢失且极难排查。
  7. last-touch 覆盖绑定：用户被反复"抢归属"，邀请人激励失真。
  8. 把绑定关系当助力记录：改绑一次就多发一份奖励。
  9. 海报尺寸写死 750×1334：换成竖屏长图或方形海报时全部错位。
  10. 中文按字符数折行：数字与英文混排时一行特别短或特别长。
  11. 忘了 revokeObjectURL：连续生成十张海报，低端机 WebView 崩掉。
  12. toBlob 返回 null 没处理：直接 createObjectURL(null) 抛异常，且错误信息与真实原因无关。

七、验收清单 ​

  • [ ] 分享失败有明确降级路径，且不阻塞抽奖；
  • [ ] JS-SDK 签名的 URL 与页面实际 URL（去 hash）一致；
  • [ ] 分享卡片在微信内、外的表现都有定义（含未验证标注）；
  • [ ] 朋友圈引导文案符合"不能 JS 触发"的限制；
  • [ ] 分享链接参数全部在 query，并带 channel 与 from；
  • [ ] 归因解析兼容 scene 的两种格式；
  • [ ] 绑定规则写明 first-touch / 归因窗口，且有自助力与改绑测试；
  • [ ] 海报布局为纯函数，有溢出与二维码位置断言；
  • [ ] 绘制顺序固定，二维码最后画；
  • [ ] DPR 与海报尺寸上限有说明，toBlob 失败有兜底；
  • [ ] Object URL 有释放逻辑；
  • [ ] 真机保存到相册的能力有明确"未验证"标注（若未验证）。
