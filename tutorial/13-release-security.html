教程 13 · 发布工程化与安全：离线包 CI、签名链与止损 ​

目标：把 10 章 的离线包从"能下载"推到"可签名、可灰度、可止损"，并给本地数据与 Bridge 划出安全边界。 版本锚点：React Native 0.87.1（bridgeless + Hermes）；react-native-blob-util@0.25.1、react-native-zip-archive@9.5.3、react-native-mmkv@4.3.2。 前置：09 · 离线能力 的本地存储、10 · WebView 离线 的 manifest / 安装 / 回滚 / JSBridge。

前两章解决"数据不丢"和"多端一致"。本章解决最后一个问题：你发出去的东西，怎么保证没被改、能撤回、出事能停。

先给结论：发布工程化的核心不是流程好看，而是每个阶段都有"拒绝发布"和"退回上一版"的能力。

一、离线包 CI：四个阶段，三道闸门 ​

1.1 阶段划分 ​

阶段输入输出失败时必须
构建H5 源码、依赖锁文件dist/ + 构建元数据阻断，不允许"本地补包"
打包dist/不可变 zip + sha256 + 大小阻断
签名zip 摘要、版本号manifest.json + 签名阻断，绝不允许跳过签名
发布签名 manifest对象存储 + 灰度配置可暂停、可回滚
yaml
# .github/workflows/offline-package.yml（示意，仓库未内置）
jobs:
  release:
    steps:
      - run: npm ci
      - run: npm run build:h5          # 产物 base: './'，见 10 章
      - run: node scripts/pack-offline.mjs   # zip + sha256 + size
      - run: node scripts/sign-manifest.mjs  # 调 KMS/HSM，不落私钥
      - run: node scripts/publish-offline.mjs --channel=gray --rollout=1

三条硬规则：

  1. 产物不可变：同一版本号永远对应同一个 zip；禁止覆盖上传。
  2. 私钥不进 CI 仓库：签名走 KMS/HSM 或独立签名服务，CI 只拿签名结果。
  3. 发布与构建分离：构建失败不能靠人工重传补丁，必须重新走完整流水线。

1.2 manifest 版本治理 ​

字段规则反例
version对外展示，语义化用提交哈希当版本，用户无法比较
buildNumber单调递增整数，防降级以它为准只比 version 字符串
minAppVersion低于此版本的 App 不安装不写，老 App 装上不兼容包
sha256内容摘要，安装前必校验只在服务端校验
rollout0–100，按设备稳定分桶每次请求随机
mandatory是否强制升级所有包都强制，用户无法回退
ts
// src/h5/releaseManifest.ts
import type { OfflineManifest } from './offlineTypes';

 * 在 10 章 manifest 基础上增加 buildNumber。
 * 防降级必须用 buildNumber，不能用 version 字符串：
 * "2026.9.10" 和 "2026.9.9" 按字符串比较会得出错误结论。
 */
export type ReleaseManifest = OfflineManifest & {
  buildNumber: number;
  channel: 'stable' | 'gray' | 'internal';
};

1.3 全量包 vs 差分包 ​

维度全量包差分包
实现复杂度低高（需基线版本、二进制 diff、端上合并）
失败模式下载失败 / 校验失败合并失败、基线不匹配、补丁链断裂
体积收益无包越大、改动越集中，收益越明显
回滚直接切指针仍需保留全量包兜底
签名对最终 zip 签名必须对"最终产物摘要"签名，不能只签补丁

取舍建议：

  • 首包与低频更新：全量包。简单、可验证、失败可重试。
  • 包体 > 10MB 且更新频繁：再考虑差分包，但必须保留全量包作为 fallback。
  • 差分包工具链需要单独核实版本与新架构无关（它是构建期工具，不进 App），本文不指定具体库，需安装时确认。

常见坑：只对补丁签名，合并后不重新校验最终产物。攻击者可以替换补丁，合并出一个未签名的包。

二、签名链：选型、轮换与防降级 ​

2.1 Ed25519 还是 RSA ​

维度Ed25519RSA（2048/3072）
签名长度短（64 字节）长（256/384 字节）
验签速度快较慢
密钥长度短长
生态支持较新，部分老系统/库不支持极广，几乎全平台
适用新项目、可控端上环境需要兼容老系统或已有 PKI

选型原则：

  • 端上验签能力必须先验证：iOS/Android 原生库是否支持、是否在目标最低系统版本可用；
  • 若已有 RSA 证书体系与轮换流程，不要为了"更现代"强行换 Ed25519；
  • 无论选哪种，验签必须在 Native 侧完成，JS 侧只接收结果。

2.2 验签流程：先验签，再谈安装 ​

ts
// src/h5/signatureChain.ts
export type KeyRing = {
  /** keyId → base64 公钥；可同时存在多把，支持轮换过渡 */
  active: Record<string, string>;
  /** 已撤销的 keyId；即使签名能验过也必须拒绝 */
  revoked: ReadonlySet<string>;
};

export type SignedRelease = {
  manifest: {
    version: string;
    buildNumber: number;
    minAppVersion: string;
    url: string;
    sha256: string;
    size: number;
  };
  keyId: string;
  signature: string; // base64
};

export interface SignatureVerifier {
  /** 由 Native 注入；不要在 JS 里手写密码学 */
  verify(keyId: string, payload: string, signature: string): Promise<boolean>;
}

/** 规范化的签名载荷：字段顺序固定，避免两端 JSON 序列化差异 */
export function canonicalPayload(manifest: SignedRelease['manifest']): string {
  return [
    manifest.version,
    String(manifest.buildNumber),
    manifest.minAppVersion,
    manifest.url,
    manifest.sha256.toLowerCase(),
    String(manifest.size),
  ].join('\n');
}

export type VerifyFailure =
  | 'unknown-key'
  | 'revoked-key'
  | 'bad-signature'
  | 'downgrade'
  | 'app-too-old';

export type VerifyResult =
  | { ok: true }
  | { ok: false; reason: VerifyFailure };

/**
 * 顺序很重要：
 * 1) keyId 必须在钥匙串里；
 * 2) keyId 不能已撤销；
 * 3) 签名必须验过；
 * 4) buildNumber 必须大于已安装版本；
 * 5) minAppVersion 必须满足。
 * 任何一步失败都不允许安装。
 */
export async function verifyRelease(params: {
  release: SignedRelease;
  ring: KeyRing;
  verifier: SignatureVerifier;
  installedBuildNumber: number;
  appVersion: string;
}): Promise<VerifyResult> {
  const { release, ring, verifier, installedBuildNumber, appVersion } = params;

  if (!ring.active[release.keyId]) return { ok: false, reason: 'unknown-key' };
  if (ring.revoked.has(release.keyId)) return { ok: false, reason: 'revoked-key' };

  const valid = await verifier.verify(
    release.keyId,
    canonicalPayload(release.manifest),
    release.signature,
  );
  if (!valid) return { ok: false, reason: 'bad-signature' };

  // 防降级：buildNumber 必须严格递增
  if (release.manifest.buildNumber <= installedBuildNumber) {
    return { ok: false, reason: 'downgrade' };
  }

  if (compareSemver(appVersion, release.manifest.minAppVersion) < 0) {
    return { ok: false, reason: 'app-too-old' };
  }

  return { ok: true };
}

/** 只比较数字段；足够处理 2026.11.1 这类版本，复杂 semver 请用成熟库 */
export function compareSemver(a: string, b: string): number {
  const pa = a.split('.').map(Number);
  const pb = b.split('.').map(Number);
  const len = Math.max(pa.length, pb.length);
  for (let i = 0; i < len; i += 1) {
    const av = pa[i] ?? 0;
    const bv = pb[i] ?? 0;
    if (av > bv) return 1;
    if (av < bv) return -1;
  }
  return 0;
}

实测（2026-11-05，iPhone 17 / iOS 26.5 模拟器，RN 0.87.1）：实测台里实现了最小原生模块 Ed25519Verifier（Swift + CryptoKit Curve25519.Signing.PublicKey.isValidSignature，通过 RCT_EXTERN_MODULE 注册；只存在于实测台，不进 academy 仓库）。用同一组 108 字节规范化载荷与两把 key 跑五组，原生结果如下：

样本原生结果JS 侧交叉校验（@noble/ed25519 3.2.0）
正确签名ok: trueok: true，首次 48–50ms（含 SHA-512 初始化），后续 4–5ms
单字节篡改（末字节追加 5）ok: falseok: false，4–5ms
错签名（64 字节随机）ok: falseok: false，0–1ms
轮换后用旧 key 验旧签名ok: falseok: false，4ms
轮换后用新 key 验新签名ok: trueok: true，4–5ms

原生侧用 Date.now() 计时均为 0ms（实际 <0.5ms），说明验签本身不是离线包安装的性能瓶颈。两侧结论一致，可以确认签名链路在 iOS 模拟器上真实跑通。

边界：传输的是 hex 编码后的载荷，真实实现必须传 canonicalPayload() 的 UTF-8 字节；verifyRelease() 的 keyId/撤销/防降级分支仍是代码级设计，未做端到端安装演练；Android 原生验签未测。

2.3 密钥轮换 ​

轮换不是"换一把钥匙"，而是一个跨版本的过程：

步骤动作风险
1生成新密钥，keyId 写入钥匙串（旧 key 保留）无
2服务端开始用新 key 签名，keyId 随 manifest 下发老 App 不认识新 key → 验签失败
3发布一个"认识新 key"的 App 版本未升级用户仍会失败
4观察覆盖率达标后，撤销旧 key未升级用户彻底无法安装新包
5清理旧 key不可逆

关键点：

  • App 必须内置"钥匙串"，而不是单把公钥；否则每次轮换都要发版。
  • 撤销列表要能下发，但"撤销"本身不能由服务端单方面决定安装——客户端仍需本地判断 keyId 是否在撤销列表。
  • 轮换窗口必须大于"用户升级 App 的 P95 周期"。这个值只能从真实升级数据里取。

设计原则：签名密钥的轮换周期与 App 发版周期绑定。没有发版能力的团队，不要设计"服务端随时换 key"的方案。

2.4 防降级：版本号与签名双重校验 ​

只校验签名不够：攻击者可以重放一个旧的、签名合法的包。防降级必须同时满足：

  1. buildNumber 严格大于已安装版本；
  2. minAppVersion 不低于当前 App；
  3. 签名有效且 key 未撤销；
  4. 灰度配置未把该版本标记为 killVersion。
ts
// src/h5/antiDowngrade.ts
export type InstalledState = {
  buildNumber: number;
  keyId: string;
};

/**
 * 本地记录"已安装的最高 buildNumber"，只升不降。
 * 即使当前版本被回滚，这个水位也不能降——
 * 否则攻击者可以先用坏包把水位拉低，再重放旧包。
 */
export async function bumpWatermark(
  read: () => Promise<number>,
  write: (value: number) => Promise<void>,
  candidate: number,
): Promise<boolean> {
  const current = await read();
  if (candidate <= current) return false;
  await write(candidate);
  return true;
}

三、灰度与止损 ​

3.1 灰度阶梯与门禁 ​

ts
// src/release/gate.ts
export type ReleaseMetrics = {
  installs: number;
  whiteScreens: number;
  jsErrors: number;
  nativeCrashes: number;
};

export type GateThresholds = {
  minSamples: number;
  whiteScreenRate: number;   // 例如 0.005 = 0.5%
  jsErrorRate: number;
  nativeCrashRate: number;
};

export type GateResult = {
  action: 'continue' | 'hold' | 'rollback';
  reasons: string[];
};

function rate(numerator: number, denominator: number): number {
  return denominator === 0 ? 0 : numerator / denominator;
}

/**
 * 门禁只回答三件事：继续放量、暂停、回滚。
 * 样本不足时一律 hold，不能用小样本下结论。
 */
export function evaluateGate(metrics: ReleaseMetrics, limits: GateThresholds): GateResult {
  if (metrics.installs < limits.minSamples) {
    return { action: 'hold', reasons: ['insufficient-samples'] };
  }

  const reasons: string[] = [];
  const white = rate(metrics.whiteScreens, metrics.installs);
  const jsError = rate(metrics.jsErrors, metrics.installs);
  const crash = rate(metrics.nativeCrashes, metrics.installs);

  if (white > limits.whiteScreenRate) reasons.push(`white-screen:${(white * 100).toFixed(2)}%`);
  if (jsError > limits.jsErrorRate) reasons.push(`js-error:${(jsError * 100).toFixed(2)}%`);
  if (crash > limits.nativeCrashRate) reasons.push(`native-crash:${(crash * 100).toFixed(2)}%`);

  if (reasons.length === 0) return { action: 'continue', reasons: [] };
  // 白屏或原生崩溃超限：直接回滚；只有 JS 错误超限可以先 hold 观察
  if (white > limits.whiteScreenRate || crash > limits.nativeCrashRate) {
    return { action: 'rollback', reasons };
  }
  return { action: 'hold', reasons };
}

3.2 kill switch 与自动停止 ​

ts
// src/release/killSwitch.ts
export type RemoteReleaseConfig = {
  /** 需要立即停止的版本（buildNumber） */
  killBuilds: number[];
  /** 是否全局暂停离线包下发 */
  paused: boolean;
  /** 灰度百分比覆盖值；null 表示用 manifest 自带值 */
  rolloutOverride: number | null;
};

export type KillDecision = 'ok' | 'blocked' | 'paused';

/**
 * 拉取失败时使用"上一次已知良好配置"，不能因为网络问题误杀全部用户。
 * 首次启动无缓存时，按"不下发新包"处理，而不是"全部回滚"。
 */
export async function fetchReleaseConfig(
  url: string,
  lastKnownGood: RemoteReleaseConfig | null,
): Promise<RemoteReleaseConfig | null> {
  try {
    const res = await fetch(url, { headers: { Accept: 'application/json' } });
    if (!res.ok) return lastKnownGood;
    return (await res.json()) as RemoteReleaseConfig;
  } catch {
    return lastKnownGood;
  }
}

export function decideByKillSwitch(
  buildNumber: number,
  config: RemoteReleaseConfig | null,
): KillDecision {
  if (!config) return 'ok';
  if (config.paused) return 'paused';
  if (config.killBuilds.includes(buildNumber)) return 'blocked';
  return 'ok';
}

自动停止的最小实现：

  1. 客户端每次启动上报"当前离线包 buildNumber + 是否白屏"；
  2. 服务端按 buildNumber 聚合；
  3. 门禁触发 rollback → 把该 build 加入 killBuilds；
  4. 客户端下次拉取配置时收到 blocked，切回上一版并停止下载该版本。

3.3 回滚 < 3 秒：只切指针，不重新解压 ​

回滚能不能快，取决于包是否已经在本机：

场景能否 < 3s原因
新旧包都在本地，只切指针 + reload通常可以无网络、无解压
需要重新下载旧包不能受网络与包大小限制
需要重启 App 或重新挂载原生容器不能进程重启不可控
React Native JS bundle 级回滚视实现可能需要重启，不能承诺 3s

实现思路：current.json 是唯一指针，回滚只改指针，然后 reload WebView。

ts
// src/h5/rollback.ts
import ReactNativeBlobUtil from 'react-native-blob-util';

const fs = ReactNativeBlobUtil.fs;

export type Reloadable = { reload(): void };

/**
 * 原子切换指针：
 * 1) 先写临时文件；
 * 2) 用 mv 覆盖 current.json；
 * 3) 再 reload。
 * 任何一步失败都保持旧指针，最坏结果是"没回滚成功"，而不是"指针写坏"。
 *
 * 注意：mv 覆盖已存在文件的行为在 iOS/Android 上可能不同，
 * 需在目标版本实测；若不支持覆盖，需先 unlink 再 mv，但会失去原子性。
 */
export async function rollbackTo(params: {
  pointerFile: string;
  previousVersion: string;
  target: Reloadable;
}): Promise<number> {
  const started = Date.now();
  const temp = `${params.pointerFile}.tmp`;
  const payload = JSON.stringify({ version: params.previousVersion, rolledBackAt: started });

  await fs.writeFile(temp, payload, 'utf8');
  await fs.mv(temp, params.pointerFile);
  params.target.reload();

  return Date.now() - started;
}

4.1 本地数据加密 ​

实测（iPhone 17 / iOS 26.5 模拟器，op-sqlite 19.0.4）：默认安装的构建 isSQLCipher() 返回 false；open({ name: 'enc.db', encryptionKey: '...' }) 直接失败（could not open database: unable to open database file (code 14)）。因此加密不是开箱能力，必须换成 SQLCipher 编译目标并重新验证读写。MMKV 的 encryptionKey 在本机可正常读写。

ts
// src/security/secureKv.ts
import 'react-native-get-random-values'; // 给 crypto.getRandomValues 提供原生 CSPRNG
import * as Keychain from 'react-native-keychain';
import { createMMKV } from 'react-native-mmkv';

/**
 * react-native-keychain@10.0.0：带 codegenConfig（type: modules），0.87 新架构可用；
 * iOS 落在 Keychain，Android 落在 Keystore / EncryptedSharedPreferences。
 * 写入同名 service 是覆盖更新，不是新增。
 */
const ACCESSIBLE = Keychain.ACCESSIBLE.WHEN_UNLOCKED_THIS_DEVICE_ONLY;

export interface SecureKeyStore {
  get(alias: string): Promise<string | null>;
  getOrCreate(alias: string, generate: () => string): Promise<string>;
  remove(alias: string): Promise<void>;
}

export const keyStore: SecureKeyStore = {
  async get(alias) {
    const item = await Keychain.getGenericPassword({ service: alias });
    return item ? item.password : null;
  },

  async getOrCreate(alias, generate) {
    const existing = await keyStore.get(alias);
    if (existing) return existing;
    const key = generate();
    await Keychain.setGenericPassword(alias, key, {
      service: alias,
      accessible: ACCESSIBLE,
    });
    return key;
  },

  async remove(alias) {
    await Keychain.resetGenericPassword({ service: alias });
  },
};

/** 32 字节随机串；不要用 Date.now / Math.random */
function newKey(): string {
  const bytes = crypto.getRandomValues(new Uint8Array(32));
  return Array.from(bytes, b => b.toString(16).padStart(2, '0')).join('');
}

export async function openSecureKv(): Promise<ReturnType<typeof createMMKV>> {
  const key = await keyStore.getOrCreate('mmkv-key-v1', newKey);
  // encryptionKey 变化会让旧数据不可读；轮换必须显式迁移
  return createMMKV({ id: 'secure-kv', encryptionKey: key });
}

行为结果
写入后读取setGenericPassword 返回成功，getGenericPassword 读回 secret-v1
同名 service 覆盖更新再写 secret-v2，读回 secret-v2（不是并存两条）

杀进程后重读simctl terminate 后重新启动，两档 accessible 的记录都读回：WHEN_UNLOCKED_THIS_DEVICE_ONLY → cross-value-1，AFTER_FIRST_UNLOCK → cross-value-2

kSecAttrAccessible 的边界：本次只验证了"模拟器解锁状态下杀进程重读"，两档都可见。按平台语义，WHEN_UNLOCKED_THIS_DEVICE_ONLY 在锁屏后不可读、且不随备份迁移；AFTER_FIRST_UNLOCK 在首次解锁后即使锁屏也可读，适合后台任务。锁屏 / 后台读取未实测（模拟器无法可靠锁定），需要真机补测。

实测：密钥丢失兜底：删除 Keychain 中的 lab.lost.key 后，用替换密钥打开同一 MMKV id，旧密文读出 null（不抛错），写入新值成功；下一次冷启动读回 new-value。结论："读空"不能当成"首次启动"，应用层必须把 get == null 判定为"密钥丢失 → 登出 + 清空该加密 KV + 重新生成密钥"，否则会把用户数据静默覆盖。

SQLCipher 的边界必须说清：

  • @op-engineering/op-sqlite@19.0.4 是否内置 SQLCipher、open() 是否接受 encryptionKey，需按目标版本 typings 与官方文档确认；本文不假设它一定支持。
  • 若不支持，两条路：使用官方 SQLCipher 构建目标，或只把敏感字段做应用层加密（后者无法防整库拖走）。
  • 加密后密钥丢失 = 数据永久不可读，必须有"密钥丢失即登出 + 清库"的兜底。

常见坑：MMKV 换 encryptionKey 后直接读旧数据。结果不是报错，而是读到空值/乱码。轮换必须伴随一次显式迁移。

4.2 Bridge 能力白名单与越权防护 ​

10 章的白名单解决"能不能加载"，这一节解决"加载后能调什么"。

ts
// src/h5/bridgePolicy.ts
export type BridgeOrigin = 'local-package' | 'remote-trusted';
export type BridgeCapability =
  | 'cache.get'
  | 'cache.set'
  | 'queue.enqueue'
  | 'profile.read'
  | 'payment.pay';

const GRANTS: Record<BridgeOrigin, readonly BridgeCapability[]> = {
  // 本地包可信，但仍不给支付能力：支付必须走原生页面/服务端
  'local-package': ['cache.get', 'cache.set', 'queue.enqueue', 'profile.read'],
  // 远程页面只读，且必须经过原生二次确认
  'remote-trusted': ['profile.read'],
};

export type BridgeRequest = {
  pageLoadId: string;   // 每次页面加载生成，防止旧页面重放
  capability: BridgeCapability;
  payload: unknown;
};

export function assertCapability(origin: BridgeOrigin, capability: BridgeCapability): void {
  if (!GRANTS[origin].includes(capability)) {
    throw new Error(`bridge denied: ${origin} -> ${capability}`);
  }
}

/**
 * 越权防护的三层：
 * 1) origin 白名单（10 章）；
 * 2) capability 白名单（本节）；
 * 3) 原生侧对敏感能力再做一次业务校验（例如支付必须校验订单归属）。
 * 只做第 1 层，等于把整个 Bridge 暴露给任何能加载的页面。
 */
export function assertBridgeRequest(
  origin: BridgeOrigin,
  expectedLoadId: string,
  request: BridgeRequest,
): void {
  if (request.pageLoadId !== expectedLoadId) throw new Error('bridge denied: stale page');
  assertCapability(origin, request.capability);
}

4.3 universal XSS：不要给 H5 开全权限 ​

universal XSS 的典型成因不是"页面有 XSS"，而是"页面有 XSS + Bridge 权限过大"。

风险配置后果正确做法
allowUniversalAccessFromFileURLs=true + 加载远程页面远程 JS 可读本地文件本地包与远程页分开实例；远程页关闭该开关
injectedJavaScript 拼接用户输入直接执行任意脚本只注入静态脚本；数据走 postMessage
source 直接传用户 HTML 字符串用户 HTML 里的脚本可调 Bridge先转义/净化，或改用纯文本渲染
onMessage 不校验来源任意页面可伪造消息校验 pageLoadId + schema + capability
Bridge 暴露 eval / 动态执行XSS 直接升级为原生能力不提供任何动态执行能力

const ESCAPE: Record<string, string> = {
  '&': '&amp;',
  '<': '&lt;',
  '>': '&gt;',
  '"': '&quot;',
  "'": '&#39;',

/** 只用于"把不可信文本放进 HTML 模板"的场景；不要用它替代完整净化库 */
export function escapeHtml(value: string): string {
  return value.replace(/[&<>"']/g, ch => ESCAPE[ch] ?? ch);
}

export type BridgeMessage = {
  pageLoadId: string;
  capability: string;
  payload: unknown;
};

/** 运行时校验：字段类型、长度、capability 是否在白名单内 */
export function isBridgeMessage(raw: unknown): raw is BridgeMessage {
  if (typeof raw !== 'object' || raw === null) return false;
  const obj = raw as Record<string, unknown>;
  return (
    typeof obj.pageLoadId === 'string' &&
    obj.pageLoadId.length > 0 &&
    typeof obj.capability === 'string' &&
    obj.capability.length > 0 &&
    'payload' in obj
  );
}

4.4 越狱 / Root：威胁模型与降级 ​

先明确一件事：越狱/Root 检测是"提高成本"，不是"安全边界"。攻击者可以 hook 检测函数、修改返回值。

威胁检测能否阻止合理降级
本地数据库被拖走不能加密 + 密钥放 Keychain/Keystore
离线包被替换不能签名 + 防降级（本章第二节）
Bridge 被恶意调用部分能力白名单 + 原生业务校验
内存抓取 token不能短时效 token + 刷新 + 设备绑定
自动化脚本刷接口部分服务端风控，不依赖客户端
ts
// src/security/deviceTrust.ts
export type DeviceTrust = 'trusted' | 'untrusted' | 'unknown';

export interface DeviceIntegrityProbe {
  /** 原生实现；检测结果随时可能被绕过，只能作为风控信号之一 */
  check(): Promise<DeviceTrust>;
}

export type SecurityPolicy = {
  allowOfflinePackageInstall: boolean;
  requireReauthForSensitive: boolean;
  allowPlaintextExport: boolean;
};

/** 越狱/Root 设备：降级而不是直接封禁，避免误伤正常用户 */
export function policyForTrust(trust: DeviceTrust): SecurityPolicy {
  if (trust === 'untrusted') {
    return {
      allowOfflinePackageInstall: false, // 防止被替换的离线包
      requireReauthForSensitive: true,
      allowPlaintextExport: false,
    };
  }
  return {
    allowOfflinePackageInstall: true,
    requireReauthForSensitive: false,
    allowPlaintextExport: true,
  };
}

五、常见坑 ​

  1. manifest 只签 url，不签 sha256 和 size：攻击者可改下载地址或替换内容。
  2. 验签用 JSON 原文字符串：两端序列化顺序不同，合法包也会验失败；必须用规范化载荷。
  3. 回滚时把防降级水位一起回退：旧包可以被重放。
  4. 灰度用随机数：同一设备每次进入不同桶，问题无法复现。
  5. kill switch 拉取失败就全量回滚：网络抖动会误伤全部用户。
  6. < 3s 回滚包含下载时间：这个承诺做不到；只能承诺"指针切换 + reload"。
  7. Bridge 只校验 URL 不校验能力：任何能加载的页面都能调支付。
  8. 把越狱检测当安全边界：检测被绕过时，数据已经泄漏。
  9. MMKV 换密钥不迁移：旧数据静默读空（跨进程实测：返回 null、getAllKeys() 为空、不抛错）。

六、验收清单 ​

  • [ ] 离线包构建、打包、签名、发布四阶段分离，产物不可变；
  • [ ] manifest 含 buildNumber、minAppVersion、sha256、rollout；
  • [ ] 私钥不出现在 CI 日志、仓库与环境变量明文；
  • [ ] 验签使用规范化载荷，错签名/篡改包/未知 key 全部拒绝；
  • [ ] key 轮换有过渡期，撤销列表生效；
  • [ ] 防降级同时校验 buildNumber 与签名，且水位不回退；
  • [ ] 灰度有样本下限，白屏/崩溃超限自动回滚；
  • [ ] kill switch 拉取失败不误杀，缓存上次良好配置；
  • [ ] 回滚只切指针，< 3s 仅指"指针 + reload"；
  • [ ] 本地敏感数据加密，密钥在 Keychain/Keystore；
  • [ ] Bridge 有 origin + capability 双层白名单，敏感能力原生二次校验；
  • [ ] 越狱/Root 只做降级策略，不作为唯一安全边界；
  • [ ] 所有接口桩与未实测项在文档中明确标注。
