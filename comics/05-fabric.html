05 · Fabric：新渲染引擎的一天 ​

一、Fabric 是谁 ​

前面几章解决了"怎么启动"（02）和"怎么调原生"（03/04）。这一章回答最后一个大问题：React 算出来的界面，是怎么变成屏幕上的像素的？

答案是一个纯 C++ 的渲染器，代号 Fabric。它的一天分六站：

text
React 交稿 → 影子树 commit → Yoga 布局 → diff 拆单 → 指令清单 → 平台 mount
1

二、第一站：JS 侧的接线员 ​

在 JS 世界里，Fabric 的前台接待叫 [ReactFabric.js](file:///Users/yangzhijie/Desktop/practice_projects/claude-code-test/_rn-source/react-native-0.87.1/Libraries/Renderer/shims/ReactFabric.js)——它是 React 官方渲染器（react-reconciler）的 RN 适配层，通过 BatchedBridge.registerCallableModule('ReactFabric') 注册成"原生可回调的模块"，原生随时能反过来叫它。

真正的手柄在 [FabricUIManager.js:L112-L157](file:///Users/yangzhijie/Desktop/practice_projects/claude-code-test/_rn-source/react-native-0.87.1/Libraries/ReactNative/FabricUIManager.js#L112-L157)：

它用 Proxy 把 global.nativeFabricUIManager（C++ 注入的 JSI 对象）包一层，对外暴露 createNode/appendChild/completeRoot 等方法，并把它们缓存住——每次渲染不再反复跨语言找方法。

还记得 02 章的 createReactNativeComponentClass 吗？它注册进 ReactNativeViewConfigRegistry 也是懒的：视图配置第一次渲染用到才登记。启动阶段一个不必要的手续都不办。

三、第二站：影子树（ShadowTree） ​

Fabric 的核心数据结构叫影子树——JS 树在 C++ 侧的"影子分身"。它不可变：每次更新不修改旧树，而是造一棵新树，像 git commit 一样带版本号（revision）。

React 处理完一次 setState，会调用 [UIManager.cpp:L191-L210](file:///Users/yangzhijie/Desktop/practice_projects/claude-code-test/_rn-source/react-native-0.87.1/ReactCommon/react/renderer/uimanager/UIManager.cpp#L191-L210) 的 completeSurface 把成果"交稿"给 Fabric。随后 [ShadowTree.cpp:L302-L333](file:///Users/yangzhijie/Desktop/practice_projects/claude-code-test/_rn-source/react-native-0.87.1/ReactCommon/react/renderer/mounting/ShadowTree.cpp#L302-L333) 执行 commit：

commit 不是总一次成功——如果期间有别的线程也在 commit（并发渲染很常见），会发生版本冲突，Fabric 会带着最新版本重试，就像 git rebase 失败后再 rebase 一次。

commit 成功后，[ShadowTree.cpp:L376-L417](file:///Users/yangzhijie/Desktop/practice_projects/claude-code-test/_rn-source/react-native-0.87.1/ReactCommon/react/renderer/mounting/ShadowTree.cpp#L376-L417) 会用新根替换旧根，并立刻调用 layoutIfNeeded()——这引出第三站。

四、第三站：Yoga 算布局 ​

Flexbox 布局引擎 Yoga 就住在影子节点里。[YogaLayoutableShadowNode.cpp:L67-L90](file:///Users/yangzhijie/Desktop/practice_projects/claude-code-test/_rn-source/react-native-0.87.1/ReactCommon/react/renderer/components/view/YogaLayoutableShadowNode.cpp#L67-L90) 把样式交给 Yoga 节点，[L174-L190](file:///Users/yangzhijie/Desktop/practice_projects/claude-code-test/_rn-source/react-native-0.87.1/ReactCommon/react/renderer/components/view/YogaLayoutableShadowNode.cpp#L174-L190) 再把算好的 x/y/宽/高写回影子节点。

关键点：布局发生在 C++，而不是 JS。JS 只声明"我想要什么样"，量尺寸的活全程不出 C++ 半步——这是新架构流畅度的基础。

五、第四五站：diff 拆单，生成指令 ​

新旧两棵树都齐了，现在需要知道"到底哪里变了"。这就是 [Differentiator.cpp:L122-L140](file:///Users/yangzhijie/Desktop/practice_projects/claude-code-test/_rn-source/react-native-0.87.1/ReactCommon/react/renderer/mounting/Differentiator.cpp#L122-L140) 的活：产出五种指令。

text
CREATE  造新视图        INSERT 挂子树
UPDATE  改属性          REMOVE 摘子树
DELETE  销毁
1
2
3

它不是傻乎乎地遍历整棵树——得益于"平化节点"优化（被 collapsable 折叠的纯布局节点），diff 在 [L195-L232](file:///Users/yangzhijie/Desktop/practice_projects/claude-code-test/_rn-source/react-native-0.87.1/ReactCommon/react/renderer/mounting/Differentiator.cpp#L195-L232) 会递归展开子树差异，一次 list 项插入也能精确到"只动这一个节点"。

指令清单交给 [MountingCoordinator.cpp:L71-L93](file:///Users/yangzhijie/Desktop/practice_projects/claude-code-test/_rn-source/react-native-0.87.1/ReactCommon/react/renderer/mounting/MountingCoordinator.cpp#L71-L93) 的 calculateShadowViewMutations 排好序。

六、第六站：mount 上屏 ​

最后一步，[MountingCoordinator.cpp:L179-L188](file:///Users/yangzhijie/Desktop/practice_projects/claude-code-test/_rn-source/react-native-0.87.1/ReactCommon/react/renderer/mounting/MountingCoordinator.cpp#L179-L188)：

mount 不做"整树替换"，而是基于 revision 增量推进：屏幕永远停在"某个版本的指令播放完"的连贯状态，旧树则被异步销毁——绝不在渲染线程上做析构。

Android 端由 FabricUIManager 逐条执行指令，iOS 端由 RCTViewComponentView（下一站再见）逐条上屏。commit 收尾时还会回发 layout events（onLayout 就是从这来的，[ShadowTree.cpp:L464-L489](file:///Users/yangzhijie/Desktop/practice_projects/claude-code-test/_rn-source/react-native-0.87.1/ReactCommon/react/renderer/mounting/ShadowTree.cpp#L464-L489)）。

七、这一章记住三件事 ​

  1. 影子树不可变 + 版本号：并发渲染不撕裂，diff 永远有确定的"两棵树"可比；
  2. 布局在 C++：Yoga 内嵌在影子节点里，JS 不参与测量；
  3. 指令化 mount：平台只听五种指令，跨端行为完全一致。

八、FAQ ​

Q1：onLayout 是在哪一步触发的？ commit 成功后由 ShadowTree 回发 layout events，经 event pipeline 回到 JS——所以它天然是异步批量的，别在 onLayout 里同步改状态指望同帧生效。

Q2：为什么我的 View 上面找不到原生层级？collapsable 的平化优化：纯布局用途的 View 会被 C++ 折叠掉，原生侧根本不存在。需要原生实体时设 collapsable={false}。

Q3：旧 Paper 渲染器还在源码里吗？ 在，作为兼容模式存在。但 bridgeless 默认走 Fabric，0.87 的新项目开箱即新渲染器。
