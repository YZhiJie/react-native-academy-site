08 · iOS 内幕：CocoaPods 交响乐团与 SwiftUI 新客 ​

如果说 Android 侧是"工厂+地道"，iOS 侧更像一支交响乐团：pod install 是指挥家点名，每个 pod 是一位乐手，bridgeless 是换新指挥棒，SwiftUI 容器则是刚入团的新客。

一、点名成军：pod install ​

模板的 Podfile 最终调用的 helpers 会把几十个 pod 组成乐团。JS 引擎的选择藏在 [scripts/cocoapods/jsengine.rb:L8-L20](file:///Users/yangzhijie/Desktop/practice_projects/claude-code-test/_rn-source/react-native-0.87.1/scripts/cocoapods/jsengine.rb#L8-L20) 的 setup_hermes!：

ruby
# jsengine.rb:L12-L21（节选）
def setup_hermes!(react_native_path: "../node_modules/react-native")
    react_native_dir = Pod::Config.instance.installation_root.join(react_native_path)
    hermestag_file = File.join(react_native_dir, "sdks", ".hermesv1version")
    hermestag = File.exist?(hermestag_file) ? File.read(hermestag_file).strip : ''
    pod 'hermes-engine', :podspec => "#{react_native_path}/sdks/hermes-engine/hermes-engine.podspec", :tag => hermestag
    pod 'React-hermes',  :path => "#{react_native_path}/ReactCommon/hermes"
end

二、乐团编制：React-RuntimeApple ​

新架构把"运行时"打成一个合集 pod：[React-RuntimeApple.podspec](file:///Users/yangzhijie/Desktop/practice_projects/claude-code-test/_rn-source/react-native-0.87.1/ReactCommon/react/runtime/platform/ios/React-RuntimeApple.podspec) 依赖四位乐手——React-CoreModules、React-RCTFabric、React-NativeModulesApple、React-runtimeexecutor。

对照 Android 章的架构图你会发现一一对应：核心模块组、Fabric 组件、原生模块、JS 执行器——两端的"编制"由同一套 C++ 核心统一，平台 pod 只负责"乐手的本地口音"。

三、指挥棒换新：bridgeless 默认 ​

旧世界的大管家 RCTBridge 还在，但门牌已摘：[RCTBridge.h:L96-L124](file:///Users/yangzhijie/Desktop/practice_projects/claude-code-test/_rn-source/react-native-0.87.1/React/Base/RCTBridge.h#L96-L124) 的构造 API 全部标注 deprecated，注释明说"随 legacy architecture 移除"：

新指挥棒由 RCTBundleManager 递上来：[RCTBundleManager.m:L103-L167](file:///Users/yangzhijie/Desktop/practice_projects/claude-code-test/_rn-source/react-native-0.87.1/React/Base/RCTBundleManager.m#L103-L167) 提供 bridgeless 的 getter/setter，[L81-L99](file:///Users/yangzhijie/Desktop/practice_projects/claude-code-test/_rn-source/react-native-0.87.1/React/Base/RCTBundleManager.m#L81-L99) 管理 bundle（本地/远程地址）的注册。

bridgeless 的实际含义：JS 运行时由 ReactHost 直接持有，不再包一层 Bridge 对象。少一层包装 = 少一批转发调用 = 启动更快、内存更省。AppDelegate 里 reactDelegate 的默认模板代码就是这条新链的入口。

四、新客入团：ReactApple / RCTSwiftUI ​

0.87 源码树里最年轻的目录是 ReactApple/，第一位住客是 SwiftUI 容器：

  • [RCTSwiftUIContainerView.swift](file:///Users/yangzhijie/Desktop/practice_projects/claude-code-test/_rn-source/react-native-0.87.1/ReactApple/RCTSwiftUI/RCTSwiftUIContainerView.swift)：Swift 声明式视图容器；
  • [RCTSwiftUIContainerViewWrapper.m](file:///Users/yangzhijie/Desktop/practice_projects/claude-code-test/_rn-source/react-native-0.87.1/ReactApple/RCTSwiftUIWrapper/RCTSwiftUIContainerViewWrapper.m)：ObjC 包装层，让 Fabric 的组件视图体系（纯 ObjC）能"雇佣"SwiftUI 员工；

五、FAQ ​

Q1：我应该手写 RCTBridge 初始化吗？ 不要。用 AppDelegate 模板的 bridgeless 路径；手写旧桥 API 会收到弃用警告，且享受不到新架构收益。

Q2：SwiftUI 容器我在 JS 里怎么用？ 作为实验性组件引入（ReactApple 路线）。生产环境仍以 Fabric 原生组件为主——新客刚入团，戏份会越来越多。

Q3：pod install 很慢/卡住怎么办？ 预编译产物（hermes-engine 等）走 CDN；确保 RCT_IGNORE_PODS 类 hack 没有破坏依赖树。国内网络建议配置 CocoaPods 镜像与 HTTPS 代理。
