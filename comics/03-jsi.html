03 · JSI：一扇穿越次元的门 ​

一、旧 Bridge 为什么必须死 ​

在"旧世界"里，JS 和原生是两个互不相通的国度，通信全靠异步快递：

  1. JS 把调用序列化成 JSON，扔进消息队列；
  2. 原生侧拆包、执行、把结果再打包寄回；
  3. 全程异步批处理——你无法"同步拿到一个值"，延迟和吞吐都卡在打包拆包上。

这个设计在 2015 年够用，但对今天的手势动画、实时列表就是灾难：一根手指在屏幕上滑动，每秒几百次事件，谁也受不了"每件事都寄快递"。

二、JSI 的真实身份：不是桥，是接口 ​

ReactCommon/jsi/jsi/jsi.h 定义了一份与具体 JS 引擎无关的 C++ 接口。理解它只需要三个概念：

概念 1：jsi::Runtime —— 电梯机房的标准插座 ​

[jsi.h:L704-L822](file:///Users/yangzhijie/Desktop/practice_projects/claude-code-test/_rn-source/react-native-0.87.1/ReactCommon/jsi/jsi/jsi.h#L704-L822) 罗列了 Runtime 的全部能力：属性的读写、对象/字符串/错误的创建、作用域管理、TypedArray……Hermes 和 JavaScriptCore 都实现了这份接口，所以上层代码（Fabric、TurboModules）完全不关心底下跑的是哪个引擎。

概念 2：HostObject —— 挂在 JS 全局对象上的 C++ 卧底 ​

[jsi.h:L205-L250](file:///Users/yangzhijie/Desktop/practice_projects/claude-code-test/_rn-source/react-native-0.87.1/ReactCommon/jsi/jsi/jsi.h#L205-L250)：

cpp
// jsi.h:L205-L250（节选示意）
// HostObject 是"由 C++ 实现属性"的对象：JS 每次 get/set
// 都会同步进入 C++ 函数 —— 无序列化、无队列、无中间商
class HostObject {
 public:
  virtual Value get(Runtime&, const PropNameID& name);      // JS 读属性 → 进 C++
  virtual void set(Runtime&, const PropNameID& name, Value); // JS 写属性 → 进 C++
  virtual std::vector<PropNameID> getPropertyNames(Runtime&); // 枚举属性
};

global.__turboModuleProxy 就是一个这样挂进 JS 全局的 HostObject——你在第 02 章见过它的用法：

js
// Libraries/TurboModule/TurboModuleRegistry.js:L17-L33（我逐行验证过）
const turboModuleProxy = global.__turboModuleProxy;   // ← C++ 卧底就位

function requireModule<T extends TurboModule>(name: string): ?T {
  if (turboModuleProxy != null) {
    const module: ?T = turboModuleProxy(name);        // 同步直达 C++！
    if (module != null) {
      return module;
    }
  }
  const legacyModule: ?T = NativeModules[name];       // 旧世界兜底
  if (legacyModule != null) {
    return legacyModule;
  }
  return null;
}

概念 3：CallInvoker —— 线程调度按钮 ​

C++ 拿到调用后，可能需要在 JS 线程上执行代码（JS 引擎不是线程安全的）。ReactCommon/callinvoker/ 提供的 CallInvoker 就是那个"把代码安全地安排到 JS 线程跑"的调度员。

五、FAQ ​

Q1：JSI 是私有 JS 引擎吗？ 不是。它是"JS 引擎适配接口"。RN 团队的 jsi 独立仓库就是它的老家，RN 里这份是配套副本。

Q2：同步调用会不会卡 UI？ 会——能力越强责任越大。所以官方模块的同步方法极少（同步存储、同步测量），普通方法依然走异步 Promise。JSI 给的是"选择权"，不是"必须同步"。

Q3：我写的业务代码需要关心 JSI 吗？ 不需要直接操作，但你写的每个 NativeModules.XXX 调用都路过它（或被它加速）。理解它，你就理解了新架构所有性能口号的物理基础。
